    使用说明与答题框架

    本篇 12 道题按三大类组织：渲染与基础概念（Q1–Q4）、路由与组件模型（Q5–Q7）、数据获取与缓存（Q8–Q12）。每题先给出【考察点】（面试官想听什么），再给【参考答案】。答题时建议套用第 79 节的五段框架：定义 → 原理 → 对比 → 场景 → 坑，下面的答案已经按这个层次展开。涉及版本差异的地方已注明，最终行为以官方文档为准。

    一、渲染与基础概念

    Q1：客户端渲染（CSR）、服务端渲染（SSR）、静态站点生成（SSG）、增量静态再生成（ISR）分别是什么？实际项目怎么选？

    【考察点】是否真正理解四种渲染策略的本质区别——HTML 在哪里、什么时候生成；能否结合业务场景做选型。

    【参考答案】

    • 定义：客户端渲染（Client-Side Rendering，CSR）由浏览器执行 JavaScript 生成 HTML；服务端渲染（Server-Side Rendering，SSR）在服务器上每次请求实时渲染出 HTML；静态站点生成（Static Site Generation，SSG）在构建时把页面预渲染成静态文件；增量静态再生成（Incremental Static Regeneration，ISR）让静态页面能在运行期按周期或按需后台更新。
    • 原理对比：首屏速度 SSG/ISR 最快（内容分发网络 CDN 边缘节点直出），SSR 居中，CSR 最慢（白屏等 JS）；SEO（搜索引擎优化）友好度上 SSR/SSG/ISR 都好，CSR 差；内容新鲜度上 SSR 实时、ISR 周期更新、SSG 构建时定格。
    • 选型：内容几乎不变的官网 / 文档 / 博客 → SSG 或 ISR；依赖登录态、个性化数据、实时价格库存 → SSR（或 CSR + 客户端请求）；内部后台、重交互工具 → CSR 足够。
    • 坑：ISR 的 revalidate 不是定时器，而是「上次生成超过 N 秒后，下一次访问触发后台再生成」，无人访问的页面不会自动更新。

    Q2：React Server Components（RSC）和传统 SSR 是一回事吗？区别在哪？

    【考察点】能否讲清 App Router 时代最核心的概念差异，避免把 RSC 当成「新的 SSR」。

    【参考答案】

    • 不是一回事。传统 SSR 是「在服务端把 React 组件渲染成 HTML 字符串」，浏览器拿到 HTML 后仍要下载完整 JavaScript 并对整棵组件树做水合（Hydration），才能交互。
    • RSC 是一种组件类型 / 渲染模型：React Server Components 在服务端渲染，其结果以一种特殊的「组件协议」数据流（RSC Payload）发给客户端；这部分组件对应的 JavaScript 根本不发给浏览器，也不需要水合。只有标记了 "use client" 的组件才作为客户端组件发 JS、做水合。
    • 对比一句话：SSR 解决「首屏 HTML 从哪来」，RSC 解决「哪些代码根本不该发给浏览器」。两者可以叠加——Next.js App Router 默认就是「服务端组件渲染 + 需要时再 SSR」。
    • 坑：服务端组件不能使用浏览器 API、不能用 React Hooks、不能持有状态；要交互的部分必须拆成客户端组件。

    Q3：next/link 和 router.push 有什么区别？什么场景用哪个？

    【考察点】对声明式导航与命令式导航的理解，以及是否知道 Link 的预取（prefetch）优化。

    【参考答案】

    • next/link 是声明式导航组件：渲染成 <a> 标签，支持右键新窗口、SEO、无障碍，并且在视口内时会自动预取目标路由的 RSC 数据，点击后近乎秒开。
    • useRouter() 来自 next/navigation（App Router；Pages Router 是 next/router），它的 router.push() 是命令式导航，用于「点击按钮后还要先做逻辑（校验、埋点）再跳转」的场景，没有自动预取。
    • 建议：能写成链接就用 Link；需要在事件回调里带条件跳转时用 router.push。

    Q4：什么是水合（Hydration）？为什么会出现水合不匹配报错？

    【考察点】是否理解 SSR / RSC 之后客户端「接管」页面的过程，以及服务端与客户端渲染结果不一致的原因。

    【参考答案】

    • 定义：水合是浏览器拿到服务端返回的 HTML 后，把事件监听、状态、生命周期绑定到已有 DOM 上，让静态 HTML 变成可交互页面的过程。
    • 不匹配的原因：服务端渲染出的 HTML 与客户端首次渲染结果不一致——常见来源有：服务端与客户端时间 / 随机数不同、直接读取了仅浏览器存在的 API（如 window）、Date.now() 两侧不同、HTML 结构不合法（如 <div> 嵌在 <p> 里）。
    • 对策：把依赖浏览器环境的逻辑放到 useEffect 里执行、用 suppressHydrationWarning 标记已知差异点（如主题类）、确保两侧初始渲染一致。

    二、路由与组件模型

    Q5：「use client」到底是什么？服务端组件和客户端组件怎么划分？

    【考察点】是否理解 App Router 默认是服务端组件，以及客户端组件的边界规则。

    【参考答案】

    • 默认规则：App Router 里所有组件默认是服务端组件；只有文件顶部写了 "use client" 的模块及其导入的组件才是客户端组件，会被打包发往浏览器。
    • 什么时候必须用客户端组件：用到浏览器 API / 事件监听（onClick 等）、React Hooks（useState / useEffect）、浏览器专属交互的组件。
    • 划分原则：尽量把组件树「外围」做成客户端组件（交互壳），「内部」内容保持服务端组件直接取数据；不要在服务端组件里 import 客户端组件后再往下传子组件作为 children——这是官方推荐的「从服务端组件向客户端组件传 children」模式。
    • 坑："use client" 是模块边界而非组件边界——一个文件写了它，整个文件都是客户端组件。

    Q6：App Router 中如何获取动态路由参数和搜索参数？

    【考察点】对 App Router 异步 API 形态的掌握（Next.js 15 起 params / searchParams 是 Promise）。

    【参考答案】

    • 服务端组件中，params 和 searchParams 是异步对象，需要 await：
    app/blog/[slug]/page.tsx
    export default async function Page({
  params,
  searchParams,
}: {
  params: Promise<{ slug: string }>
  searchParams: Promise<{ q?: string }>
}) {
  const { slug } = await params
  const { q } = await searchParams
  return <div>文章 {slug}，搜索词 {q}</div>
}
    • 客户端组件中用 useParams()、useSearchParams()（来自 next/navigation）同步读取。
    • 注意：Next.js 15 起 params / searchParams 从同步改为 Promise，旧代码直接解构会报错（以官方文档为准）。

    Q7：Pages Router 的 getServerSideProps / getStaticProps 在 App Router 里等价于什么？

    【考察点】能否完成新老路由范式的映射，理解「数据获取回归组件本身」。

    【参考答案】

    • getServerSideProps（每次请求取数据）→ App Router 中直接在异步服务端组件里 await 数据请求；用到 cookies / headers / searchParams 等动态 API 时路由自动变为动态渲染。
    • getStaticProps（构建时取数据）→ 服务端组件取数据 + generateStaticParams() 生成动态路由的静态参数。
    • getStaticPaths → generateStaticParams。
    • 核心思想变化：不再有独立的数据获取函数，数据请求就在组件里完成，配合请求记忆与数据缓存自动优化。

    三、数据获取与缓存

    Q8：Next.js 的缓存有哪几层？各自的生命周期是什么？

    【考察点】这是 Next.js 面试最高频的题之一。能否说清四层缓存的位置与生命周期。

    【参考答案】

    Next.js 四层缓存
    缓存层位置作用生命周期
    请求记忆 Request Memoization服务端一次渲染内复用相同 fetch，避免重复请求单次请求，渲染结束即清空
    数据缓存 Data Cache服务端跨用户、跨部署持久存储 fetch 结果持久，可 revalidate 或 no-store 退出
    完整路由缓存 Full Route Cache服务端缓存静态路由的 HTML 与 RSC 产物持久，重新部署即清空
    客户端路由缓存 Router Cache浏览器导航时缓存 RSC 载荷，减少重复请求会话级 / 按时间过期
    • 记忆要点：请求记忆活在一次请求里，数据缓存活在请求之间；数据库客户端（如 Prisma）不自动享受请求记忆，需用 React 的 cache() 手动包裹。

    Q9：fetch 在 Next.js 里的缓存行为？Next.js 15 有什么重要变化？

    【考察点】是否知道版本默认值变化，避免答出过时结论。

    【参考答案】

    • 定义：Next.js 扩展了服务端 fetch，可通过选项控制是否写入数据缓存：next: { revalidate: N } 表示按 N 秒周期缓存；cache: 'no-store' 表示每次请求实时拉取。
    • 版本变化：Next.js 13/14 中 fetch 默认进入数据缓存；从 Next.js 15 起，fetch 默认不再缓存（等价 no-store），需要缓存要显式 opt-in（以官方文档为准）。
    • 面试话术：「默认行为在 15 改了，现在要缓存必须显式声明 revalidate 或 force-cache」——这句能直接区分是否跟进过版本。

    Q10：revalidate 的语义是什么？ISR 是怎么工作的？

    【考察点】是否真正理解「后台再生成 + 旧页面兜底」的语义，而不是背定时器。

    【参考答案】

    请求页面
    →
    命中旧静态页
    (可能已过期)
    →
    先返回旧页面
    后台触发再生成
    →
    生成完成
    替换缓存
    • 语义：revalidate: N 表示「页面上次生成后超过 N 秒，下一次访问时在后台重新生成」；期间用户看到的仍是旧页面（stale-while-revalidate）。
    • 坑：没有访问就不会触发更新；要精确时效用 on-demand revalidation（按事件主动触发 revalidatePath / revalidateTag）。

    Q11：客户端组件里怎么做数据请求？SWR 是什么？

    【考察点】是否知道客户端取数与服务端取数的分工，以及缓存复用类库的价值。

    【参考答案】

    • 服务端组件里直接 async / await fetch；客户端组件需要取数时，通常用客户端数据请求库。SWR（Stale-While-Revalidate）是 Vercel 开源的 Hooks 库，提供缓存、去重、自动重新验证、聚焦刷新。
    • 等价选择还有 TanStack Query（原 React Query）。选型考虑：SWR 轻量、与 Next.js 同出一门；TanStack Query 功能更全（缓存策略、分页、失效管理更丰富）。

    Q12：Next.js 里如何做 SEO（搜索引擎优化）？Metadata API 怎么用？

    【考察点】是否掌握基于文件 / 基于配置的两种 Metadata 写法，以及 sitemap、robots。

    【参考答案】

    • 在页面文件中导出 metadata 对象，或导出 generateMetadata 函数根据动态参数生成标题 / 描述 / Open Graph：
    app/blog/[slug]/page.tsx
    export async function generateMetadata({ params }) {
  const { slug } = await params
  const post = await getPost(slug)
  return {
    title: post.title + ' | 我的博客',
    description: post.excerpt,
  }
}

// 基于文件：app/opengraph-image.png、app/sitemap.ts、app/robots.ts
// 会被框架自动转为对应路由
    • 配合 SSG / ISR 输出完整 HTML，爬虫即可直接拿到内容；再用 app/sitemap.ts、app/robots.ts 生成站点地图与爬虫规则。
    本篇速记清单›

    面试前再过一遍这十二句结论：① 四种渲染看「HTML 在哪生成」；② RSC ≠ SSR，RSC 的 JS 不下发；③ Link 声明式带预取，router.push 命令式；④ 水合不匹配多因两侧渲染不一致；⑤ 默认服务端组件，"use client" 划边界；⑥ Next.js 15 起 params / searchParams 是 Promise；⑦ getServerSideProps → 组件内直接取数；⑧ 四层缓存各有生命周期；⑨ Next.js 15 fetch 默认不缓存；⑩ revalidate 是惰性后台再生成；⑪ 客户端取数用 SWR / TanStack Query；⑫ metadata + SSG 做 SEO。
