    组合方向：服务端 → 客户端是单向的

    RSC 有一条经常被面试追问的规则：服务端组件可以渲染客户端组件，但客户端组件不能"直接"渲染服务端组件。理解它的关键，是回到上节那个打包事实——客户端组件的代码会被整个打进浏览器 bundle。

    如果你在一个客户端组件文件里 import 了一个服务端组件，打包器为了能把这个客户端组件跑起来，就会把它 import 的所有东西一并打进 bundle。可服务端组件往往连着数据库、文件系统，这些根本不存在于浏览器——所以这条路必须被编译器掐断。

    服务端组件 Page
    （不进 bundle）
    →
    渲染客户端组件 Shell
    （进 bundle）
    →
    把服务端子树
    作为 children 传入
    →
    子树在服务端就已序列化
    随 Flight 流送达

    正确姿势：用 children 做"缝隙"

    官方推荐的模式叫组合（Composition）：服务端组件在自己这一层，把"想塞进客户端组件内部的服务端内容"作为 children 传下去。客户端组件只管布局和交互，至于 children 里是什么，它根本不关心——那是一段已经序列化好的 Flight 数据。

    正确：服务端组件把服务端内容作为 children 传入
    // Page.js（服务端组件，无 "use client"）
import Shell from "./Shell.js";       // Shell 是客户端组件
import Sidebar from "./Sidebar.js";   // Sidebar 也是服务端组件

export default function Page() {
  return (
    // Shell 在客户端跑；Sidebar 在服务端跑，结果作为 children 传进去
    <Shell>
      <Sidebar />
    </Shell>
  );
}

    对照上节的编码器：Shell 在 Flight 流里是一条 {t:"client", module:"Shell"} 记录，它的 children 字段指向 Sidebar 序列化出来的那批节点 id。Sidebar 的代码从头到尾没有进浏览器，进浏览器的只是它渲染出的内容。

    错误：客户端组件直接 import 服务端组件
    // Shell.js（文件顶部写了 "use client"）
import Sidebar from "./Sidebar.js"; // 不行！
// Sidebar 连着数据库，会被一起打进浏览器 bundle，直接报错。

export default function Shell({ children }) {
  // 正确做法：用调用方传进来的 children，而不是自己 import
  return <div className="shell">{children}</div>;
}
    跨边界引用对错对照
    做法是否允许原因
    服务端组件渲染客户端组件允许这正是 RSC 的用途，流里只发模块引用
    服务端组件把服务端子树作 children 传给客户端组件允许子树在服务端已序列化，作为数据传递
    客户端组件里 import 服务端组件并直接使用禁止import 链会把服务端模块卷进客户端 bundle
    客户端组件通过 props 接收一个服务端组件实例允许（即 children 模式）实例已是序列化后的 Flight 数据，不是代码

    异步组件与 Suspense：让流"分批"到达

    上节的编码器是一次性把整棵树编码完才输出。但真实 RSC 里，服务端组件可以是 async 的——它要 await 一次数据库查询。如果傻等查询完才开始发流，用户就得盯着白屏。Suspense 的作用是：遇到还没准备好的部分，先把 fallback（骨架屏）发出去，数据到了再补发一段。

    第 1 批：外壳 + Suspense fallback（骨架屏）
    ↓
    浏览器先把骨架屏画出来，不白屏
    ↓
    服务端数据库查询完成，异步组件 resolve
    ↓
    第 2 批：补发该占位符对应的真实内容
    ↓
    浏览器把骨架屏替换成真实内容

    把编码器升级成"边出边补"

    我们给上节的 renderToFlight 加两点能力：① 支持遇到 Promise 就先记下一个"占位 id"并立刻发出 fallback；② 收集这些待处理的 Promise，等它们 resolve 后再补发后续记录。下面是教学简化版的流式编码器（真实实现见 react-server-dom-webpack 的 FlightServerPlugin）。

    mini-rsc/stream-server.js（支持 Suspense 的服务端）
    // ===== 支持 Suspense 的流式 Flight 编码器（教学简化版）=====

let seq = 0;
const nextId = () => String(seq++);

// pending：等待 resolve 的异步任务，每项记录"占位 id"
const pending = [];

function isSerializable(v) { /* 同 73 节，略 */ return v == null || ["string","number","boolean"].includes(typeof v); }

function render(element, out) {
  const myId = nextId();

  if (typeof element === "string" || element == null) {
    out.push([myId, { t: "text", text: String(element ?? "") }]);
    return myId;
  }
  const { type, props } = element;

  // 客户端组件：只发引用（同 73 节）
  if (type.__moduleId) {
    const safeProps = {};
    for (const k of Object.keys(props)) {
      safeProps[k] = k === "children" ? render(props.children, out) : props[k];
    }
    out.push([myId, { t: "client", module: type.__moduleId, props: safeProps }]);
    return myId;
  }

  // 关键：遇到 Suspense 边界
  if (type === Suspense) {
    // 立刻把 fallback 渲染出去 —— 这是用户马上能看到的内容
    const fallbackId = render(props.fallback, out);
    // 再给真正的 children 分配一个占位 id
    const placeholderId = nextId();
    out.push([placeholderId, { t: "pending", fallback: fallbackId }]);
    // 不 await！先记下来，等 children resolve 后再补发
    Promise.resolve(props.children).then((resolved) => {
      const batch = [];
      const realId = render(resolved, batch);
      // 补发：一条"把 placeholderId 指向 realId"的记录
      pending.push([["resolve", placeholderId, realId]].concat(batch));
    });
    return placeholderId;
  }

  // 普通服务端组件：调用它。它可能返回 Promise（async 组件）
  if (typeof type === "function") {
    const result = type(props);
    // 这里简化：直接接成 Promise 交给外层 Suspense 处理
    return Promise.resolve(result).then((el) => render(el, out));
  }

  // 原生标签
  const kids = (props.children || []).map((c) => render(c, out));
  out.push([myId, { t: "host", tag: type, kids }]);
  return myId;
}

// 触发流式输出：先 flush 外壳，再逐批 flush 异步结果
async function encodeStream(root) {
  const shell = [];
  const rootId = await render(root, shell);
  // 第 1 批：外壳（含骨架屏 fallback）立即发出
  yield JSON.stringify([rootId]) + "\n";
  for (const row of shell) yield JSON.stringify(row) + "\n";
  // 等所有异步 children resolve，逐批补发
  while (pending.length) {
    const batch = pending.shift();
    for (const row of batch) yield JSON.stringify(row) + "\n";
  }
}

// Suspense 只是一个标记类型，真实项目由 react 提供
function Suspense() {}
Suspense.__isSuspense = true;

    浏览器侧的对应升级也很小：解析到 {t:"pending", fallback} 节点时，先把 fallback 画出来；之后收到 ["resolve", placeholderId, realId] 记录时，再把 fallback 替换成 realId 对应的真实内容。这就是流式服务端渲染（Streaming Server Rendering）配合 Suspense 的最小闭环。

    你可以在脑中跑一遍：一个 async 服务端组件要查库 300ms。没有 Suspense 时，浏览器要干等 300ms 才收到任何字节；有了它，第一个字节在几毫秒内就到了（带着骨架屏），300ms 后真实内容补上。这就是 React 官方博客所说的"边取数据边输出 HTML"。

    特别要澄清一点（官方 RSC 示例仓库 README 里也强调过）：RSC 和 SSR 是两项互补但独立的技术。RSC 解决"组件零 bundle、服务端直连数据"；SSR 解决"首屏就有 HTML"。真实的 Next.js App Router 是把两者叠加：服务端组件先编成 Flight 流，同时外壳走 SSR 输出 HTML，浏览器一边解析流一边把客户端组件水合上去。

    常见坑：children 才是合法的"跨缝"方式›

    很多初学者想在客户端组件里 import 一个服务端组件来"组合布局"，这是被明确禁止的。记住一句口诀："服务端组件可以走向客户端，客户端组件不能回头找服务端组件；想缝起来，就用 children/props 传实例。"这条规则理解了，RSC 的目录结构（app/ 下全是服务端组件，只有标了 'use client' 的才进客户端）就顺理成章了。

    提示：流式不是 SSR 的专利›

    本节的"先发骨架、后补内容"思路，和第 71 节提到的 renderToPipeableStream 是同一套思想。区别在于：SSR 流式补的是 HTML 片段，RSC 流式补的是 Flight 节点记录。下一节（75「RSC 实现原理」与 76「实现 Streaming」）会分别深入这两条线的源码细节。
