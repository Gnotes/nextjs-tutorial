源码篇 | 实现 Server Actions

Server Action 让你"像调普通函数一样"在服务端改数据，不必手写接口路由。本节拆解它的协议：'use server' 编译后变成什么、浏览器如何把一次调用 POST 到服务端、服务端如何按 id 找到并执行对应函数、以及无 JavaScript 时的渐进增强。最后给一个客户端引用 + 服务端 dispatch 的最小实现。代码均为教学简化实现，真实实现见 react 源码与 next.js。

    Server Action 是什么

    在传统前后端分离里，"改数据"要写三段：前端 fetch('/api/comment', {method:'POST'}) → 手写一个接口路由 → 路由里操作数据库。Server Action（服务端动作）把这三段收成一段：你直接写一个标注 'use server' 的异步函数，在服务端执行；前端像调用普通函数一样调用它，框架负责把"调用"变成一次网络往返。

    app/actions.js（用户视角）
    // 'use server' 告诉框架：这个函数只在服务端运行
'use server';

export async function createComment(formData) {
  const text = formData.get("text");
  await db.comment.create({ data: { text } }); // 直接操作数据库
  revalidatePath("/comments");
}

    前端把它传给表单：<form action={createComment}>。看起来是"把函数当 prop 传"，但这个函数根本没有发到浏览器——浏览器拿到的只是它的一个"引用"。本节就拆这个魔法。

    'use server' 的编译产物：action id 与 server reference

    编译期，打包器看到 'use server'，做两件事：

    • 这个函数的真实实现只留在服务端 bundle里，绝不进入客户端 JS 包（数据库、密钥都安全）。
    • 给它生成一个唯一 action id，并在客户端生成一个"桩函数（stub）"：这个桩的签名和原函数一样，但调用它时并不执行逻辑，而是发起一次网络请求，把 id 和参数发出去。
    编译后客户端拿到的东西（教学示意）
    // 客户端 bundle 里根本没有 createComment 的实现，只有这个桩
const createComment = async (...args) => {
  // 把 action id 和参数 POST 回服务端
  return callServer("act_createComment_8f3a", args);
};

// 这个 id 是编译期分配的，服务端维护着 id -> 真函数 的注册表
// serverRegistry = {
//   "act_createComment_8f3a": async (formData) => { ...真实现... }
// }

    所以"前端调用函数"本质是：调用桩 → POST 一个带 id 的请求 → 服务端查表执行真函数 → 返回结果。

    一次调用的网络协议

    前端调用桩函数
    →
    POST 当前路由 URL
    带 action id + 参数
    →
    服务端解析 id
    查注册表执行
    →
    序列化返回值
    (Flight 流)
    →
    前端拿到结果
    请求的关键特征
    项说明
    请求方法POST（修改数据，不用 GET）
    目标 URL通常就是当前页面的路由地址（无需你单独建接口路径）
    Content-Type渐进增强走 multipart/form-data（原生表单能直接 POST）；带 JS 的调用会序列化参数
    请求体里有什么action id（定位要执行哪个函数）+ 序列化后的参数（含 bound args，见下）
    响应服务端把函数返回值（或要更新的界面）用 Flight 流送回

    bound args（预绑定参数）

    有时候你想先给函数"绑"一部分参数，再交给按钮。例如 deletePost.bind(null, postId)。编译期会把 postId 这类 bound args 一并序列化进 action 引用；服务端执行时把"绑好的参数 + 调用时传的参数"拼起来再调用真函数。

    渐进增强：没有 JavaScript 也能用

    这是 Server Action 最被称道的一点：当 <form action={someAction}/> 直接从服务端组件渲染出来时，哪怕浏览器完全禁用了 JS，表单也能正常工作。因为它本质就是一个原生表单——浏览器原生 POST 出去（multipart/form-data），服务端识别这是一次 action 提交，执行函数，再返回一个新页面。等 JS 水合完成后，后续提交才被拦截成异步请求、局部刷新。

    注意：客户端组件里的表单要先水合›

    渐进增强只在"服务端组件直接把 action 传给 form"时开箱即用。如果 action 是在客户端组件里经 bind 等处理后传给 form，那么 JS 未加载时提交会被排队，等水合后再执行——此时表单仍可点，但不会立刻服务端响应。以官方文档为准。

    返回值的序列化限制

    服务端函数的返回值要跨网络回到浏览器，因此和 props 一样必须可序列化：可以返回对象、数组、字符串、数字、redirect()、revalidatePath() 这类特殊指令；不能直接返回函数、类实例、数据库连接句柄。入参同理（FormData、普通对象可以，函数不行）。

    安全：它是一个 URL 可达的接口

    这是最容易被忽略、也最危险的一点：Server Action 一旦存在，任何人都可以用 curl 直接向那个 URL 发 POST 来调用它。它不是"只能从你前端页面触发"的私有函数。所以：

    • 函数内部必须自己做鉴权（这个用户是谁？有没有权限删这条评论？），不能假设"能调到我的页面就是合法用户"。
    • 必须做输入校验（用 Zod 等），因为入参来自不可信的网络请求。
    • 越权检查（这条数据属于这个用户吗？）永远在服务端做。

    最小实现：客户端引用 + 服务端 dispatch

    下面用约 50 行代码演示整套协议：客户端把 action 变成一个带 id 的桩，服务端按 id 分发执行。教学简化实现，真实实现见 react 源码 react-server-dom-webpack 与 next.js。

    action-server.js（教学简化）
    // ---- 服务端：维护 id -> 真函数 的注册表 ----
const serverRegistry = {};

// 把一个 'use server' 函数注册进去，分配 id
function registerAction(fn) {
  const id = "act_" + Math.random().toString(36).slice(2, 8);
  serverRegistry[id] = fn;
  return id;
}

// 这是用户写的服务端函数
async function createComment(formData) {
  const text = formData.get("text");
  return { ok: true, saved: text };
}
const actionId = registerAction(createComment);

// ---- HTTP 路由：拦截 POST，按 id dispatch ----
async function handleActionRequest(req) {
  // 请求体形如：{ "id": "act_xxx", "args": [formData对象] }
  const body = await req.json();
  const fn = serverRegistry[body.id];
  if (!fn) return new Response("Unknown action", { status: 404 });

  // 服务端必须在这里做鉴权 + 输入校验（此处略）
  const result = await fn(...body.args);
  // 返回值序列化成 JSON（真实实现用 Flight 流）
  return new Response(JSON.stringify(result), {
    headers: { "Content-Type": "application/json" }
  });
}
    action-client.js（教学简化）
    // ---- 客户端：编译期生成的桩函数 ----
function callServer(id, args) {
  return fetch(window.location.pathname, {
    method: "POST",
    headers: { "Content-Type": "text/plain;charset=UTF-8" },
    body: JSON.stringify({ id, args })
  }).then(r => r.json());
}

// 编译期把 createComment 替换成这个桩（id 来自编译产物）
const createComment = (...args) => callServer("act_8f3a21", args);

// 业务侧用起来毫无感知：
document.querySelector("form").addEventListener("submit", async (e) => {
  e.preventDefault();
  const fd = new FormData(e.target);
  const res = await createComment(fd);   // 看起来就是个普通函数调用
  console.log("保存结果：", res);
});

    对照真实实现你会发现：React/Next.js 在这个最小模型上补了三件事——把返回值也走 Flight 流以便顺带更新界面、支持原生表单渐进增强（multipart/form-data）、以及bound args 与多参数的完整序列化。但"注册 id → POST → 查表执行"这条主干，和上面这段代码一模一样。

    常见坑：把 Server Action 当成"私有函数"›

    因为它藏在前端代码里看不到，很多人误以为它"外部调不到"。错——它是一个 POST 接口。任何知道这个端点的人都能构造请求。鉴权、权限、限流、输入校验一个都不能少，尤其涉及删除、支付、改密的 action。

    提示：观察一次真实调用›

    在 Next.js 里提交一个用 Server Action 的表单，打开 Network 面板：你会看到一个 POST 到当前页面 URL 的请求，请求头里有 Next-Action（真实实现里带 action id），响应是一段 Flight 文本。对照本节的 dispatch 模型读一遍，立刻通透。

    最佳实践：action 内部统一做校验与鉴权›

    养成固定套路：每个 action 开头先 const session = await auth() 鉴权，再用 Zod schema 校验 formData，通过后才动数据库。把这步抽成公共函数复用，避免在某个 action 里漏掉鉴权。这是 Server Action 模式下最重要的安全习惯。
