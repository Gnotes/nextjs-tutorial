    从手写 JSON 到真实协议：本节要解决什么

    在第 73、74 节里，我们手写了一个"最小 RSC"：服务端把组件树递归遍历，把它变成一段 JSON 字符串发回浏览器，浏览器再把这份数据"还原"成 React 元素渲染出来。那个实现能跑通主流程，但它和 React 官方的实现有两个本质差距：

    • 一次性 vs 流式：手写版是 JSON.stringify(tree)——必须等整棵树、包括所有 await 都完成，才能输出一个完整字符串。真实实现要求"边算边发"，快的内容先到。
    • JSON vs Flight：手写版用普通 JSON 无法表达"这是一个客户端组件的引用"、"这个值还没算完"这类语义。真实实现用一套专门的、逐行（line-delimited）的序列化格式——Flight 协议。

    本节就是把这两个差距补齐。我们会逐行拆开真实 RSC 的输出，看清 react-server-dom-webpack 这个包在编译期与运行期分别承担什么角色。

    服务端组件树
    (RSC)
    →
    Flight 编码
    (renderToPipeableStream)
    →
    流式 payload
    (文本流)
    →
    Flight 解码
    (createFromReadableStream)
    →
    客户端 React 渲染

    Flight 协议：RSC 的"序列化语言"

    为什么不能直接用 JSON

    JSON 有三个硬伤，让它不适合做 RSC 的传输格式：

    1. 不能流式：JSON.parse 必须拿到完整字符串才能开始解析，没法"来一行解一行"，与第 76 节要讲的流式输出冲突。
    2. 无法表达引用：组件树里出现一个客户端组件（Client Component）时，服务端根本拿不到它的代码，只能发出一个"指针"；普通 JSON 没有内建的引用（reference）类型。
    3. 无法表达 pending 值：async 组件里 await fetch() 的结果要稍后才到，JSON 里没有"这个位置将来会被补上"的占位概念。

    Flight 就是为解决这三点设计的：它是一种逐行、可流式、带引用表的文本协议。每一行是一条独立记录，格式为 模型ID: 载荷，其中"模型（model）"是一个被数字编号的对象/数组。

    一条真实 Flight payload 长什么样（教学简化）

    下面这段是把一个服务端页面（里面引用了客户端组件 <Button/>）序列化后的输出。为便于阅读做了简化，但行结构与官方一致：

    .rsc payload（逐行，教学简化）
    # 第 0 号模型：根。描述整棵服务端渲染出来的树（这里只摘关键行）
0:{"children":[{"type":"div","props":{"className":"card"}},
 {"type":"$1","props":{"label":"保存"}}]}

# 第 1 号模型：一个"客户端组件引用"。
# type 不是真实组件，而是指向客户端模块的指针
1:{"$$typeof":"react.client.reference",
   "id":"./Button.js",
   "name":"default",
   "chunks":["static/chunks/button-a1b2.js"]}

# 第 2 号模型：一个还没 resolve 的 Promise 占位（await 边界）
2:{"$":"","id":"2:","status":"pending"}

# 稍后数据 ready，追加一段：把第 2 号位置补上真实值
2:{"$":"","id":"2:","status":"resolved","result":{"user":"Alice"}}

    读懂这四行，就抓住了 Flight 的全部精髓：

    • 根模型（0:）里的 "type":"$1" 是一个引用，意思是"这里的组件去第 1 号模型找"。这种"用 $数字 跨行引用"的写法，让整棵树可以拆成多行、边下面边渲染。
    • 第 1 号模型是 client reference：它不携带 Button 的代码，只告诉客户端"去加载哪个 chunk（chunks）、用哪个导出名（name）"。真实格式里 $$typeof 是一个 react.client.reference 标记。
    • 第 2 号模型演示了 await 的流式边界：先输出 pending 占位，数据好了再追加一行把它替换成 resolved。这就是"shell 先到、数据后补"在协议层的体现。
    注意：真实 Flight 的行格式比这更紧凑›

    上面为了可读用了 JSON 风格缩进。真实的 react-server-dom-webpack 输出是单行紧凑的、以冒号分隔的记录流，并会把重复的字符串/模块抽到独立模型行以减小体积。本节只演示协议思想，逐字符的编码细节请直接读 react 仓库里 react-server-dom-webpack 的 ReactFlightServer / ReactFlightClient。

    react-server-dom-webpack：编译期与运行期的分工

    这个包是 RSC 能跑起来的"胶水层"，它分两个阶段工作：

    react-server-dom-webpack 的两个阶段
    阶段做什么产物
    编译期
    (bundler 插件)    		扫描所有标注 'use client' 的模块，建立"模块 id → 要加载的 chunk 文件列表"的映射表（client manifest）一份客户端模块清单；同时给服务端侧生成对应的 server 侧引用
    运行期·服务端用 renderToPipeableStream 遍历 RSC 树；遇到客户端组件，就不渲染它，而是从 manifest 查出它的 id/chunks，输出一条 client referenceFlight 文本流（上一节那种逐行输出）
    运行期·客户端用 createFromReadableStream 逐行读流；遇到 client reference 就按 chunks 动态 import() 加载真组件，再继续渲染可水合的真实 React 元素树

    编译期：打包器如何知道哪些是客户端模块

    当你在文件顶部写了 'use client'，打包器（bundler，webpack / Turbopack）会把这个模块标记为"客户端模块"，并生成一份映射。下面是编译后"客户端侧"大致长什么样的教学示意：

    编译产物示意（client-manifest.json）
    {
  "./Button.js": {
    "default": {
      "id": "./Button.js",
      "chunks": ["static/chunks/button-a1b2.js"],
      "name": "default"
    }
  },
  "./Dialog.js": {
    "default": {
      "id": "./Dialog.js",
      "chunks": ["static/chunks/dialog-c3d4.js"],
      "name": "default"
    }
  }
}

    服务端渲染时，一旦在组件树里碰到 <Button />，渲染器查这张表，拿到 id / chunks / name，写成一条 client reference 输出——这就是上一节第 1 号模型的来源。

    async 组件与 await 的流式边界

    服务端组件可以是 async 函数，内部直接 await 取数据。React 的协调器在遍历时遇到一个尚未 resolve 的 Promise，并不会卡住整个流，而是：

    遍历到 await fetch() 的位置
    ↓
    先输出一个 pending 占位行（标记该 id 待定）
    ↓
    继续输出其它不依赖它的内容（shell 先行）
    ↓
    数据 resolve 后，追加一行把该 id 替换成真实结果

    对客户端而言，它逐行读流：读到 pending 就先在该位置挂一个 Suspense 边界显示 loading；等到后续那行 resolved 到达，再把真实内容"补"进去。这与第 10 节讲的 Suspense、第 76 节要手写的 Streaming 是同一套机制在不同层的投影。

    payload 如何最终到达浏览器

    很多人困惑：RSC 的 Flight 流和超文本标记语言（HyperText Markup Language，HTML）是什么关系？分两种请求：

    首次加载 vs 客户端导航
    场景服务端产出浏览器收到
    首次打开页面一边渲染 HTML 壳，一边把 RSC 结果作为 Flight 流内嵌/紧随在 HTML 中输出完整 HTML（含可见内容）+ 紧随其后的 Flight payload，水合时用
    点击 Link 客户端导航不再生成整页 HTML，只对 Accept: text/x-component 的请求返回一段纯 Flight payload只有 payload；客户端 React 用它增量更新视图，不刷新整页

    可以这样记：HTML 负责"第一眼看得见"，Flight payload 负责"把服务端组件树交给客户端 React 接管"。首次访问两者一起给；后续导航只给 payload，更省。

    一个最小 Flight 编码 / 解码示例

    下面用一段 Node 代码演示 Flight 的核心思想：把一棵树编码成逐行文本，再在另一端逐行还原。这是教学简化实现，真实实现见 react 源码 react-server-dom-webpack。

    mini-flight.js（教学简化）
    // 教学简化：只支持 元素 / 字符串 / 数字 / client引用 四种值
let nextId = 0;

// 把一棵树编码成 ["id:payload", ...] 的行数组
function encode(root) {
  const lines = [];

  function put(value) {
    const id = nextId++;
    // 遇到客户端组件引用，记录一个特殊模型
    if (value && value.__clientReference) {
      lines.push(`${id}:{"type":"$client","id":"${value.id}",` +
                 `"chunks":${JSON.stringify(value.chunks)}}`);
    } else {
      lines.push(`${id}:${JSON.stringify(value)}`);
    }
    return `$${id}`; // 返回一个对本行的引用
  }

  // 简化的元素序列化：type 若指向 client 组件，则换成引用
  function walk(node) {
    if (typeof node !== "object" || node === null) return put(node);
    if (node.type === "client") {
      const ref = put(node.ref);        // 先记录 client reference 行
      return { type: ref, props: node.props };
    }
    return put(node);
  }

  walk(root);
  return lines.join("\n");
}

// 解码：读入行数组，还原成"可渲染描述"
function decode(text) {
  const models = {};
  for (const line of text.split("\n")) {
    const idx = line.indexOf(":");
    const id = line.slice(0, idx);
    models[id] = JSON.parse(line.slice(idx + 1));
  }
  // 把 "$数字" 引用替换成真实模型
  function resolve(node) {
    if (typeof node === "string" && node[0] === "$") return models[node.slice(1)];
    if (node && typeof node === "object") {
      for (const k of Object.keys(node)) node[k] = resolve(node[k]);
    }
    return node;
  }
  return resolve(models["0"]);
}

// 用例：一个 div 里套了一个客户端 Button
const tree = {
  type: "div",
  props: {
    children: { type: "client",
               ref: { id: "./Button.js", chunks: ["button-a1b2.js"] } }
  }
};
const payload = encode(tree);
console.log(payload);          // 逐行 Flight 文本
console.log(decode(payload));  // 还原后的树（client 引用已指向真实模型）

    对比第 73、74 节的手写版，这里的关键差别就两点：值被拆成带编号的独立行（于是可以一行行地发、一行行地解），以及客户端组件不再内联、而是退化成一条引用行。真实 react-server-dom-webpack 只是在此之上补全了 Promise 占位、二进制流、字符串表压缩等工程细节。

    常见坑：跨边界传值必须"可序列化"›

    服务端组件传给客户端组件的 props，最终都要走 Flight 编码。因此你不能在它们之间传递函数、类实例、Symbol、模块引用等不可序列化的值。这也是为什么"把服务端函数当 prop 传给客户端组件"会直接报错——服务端函数根本不会出现在浏览器里，自然无法被调用。
