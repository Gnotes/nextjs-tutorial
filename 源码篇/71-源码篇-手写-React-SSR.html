    本节定位：为什么要手写一遍 SSR

    在第 8 节里，我们把 SSR 描述成"在服务器上把 React 组件渲染成 HTML 字符串返回浏览器，再由浏览器水合"。这句话听起来简单，但真要手写出来，会立刻撞到一堆问题：服务端没有浏览器的文档对象模型（Document Object Model，DOM），document 从哪来？事件监听在 HTML 字符串里根本不存在，页面凭什么能点？水合到底做了什么？

    这一节不使用 Next.js、不使用 Express 之外的任何框架，只用 react、react-dom/server 与 Node 内置的 http 模块，手写一个最小但完整可运行的 SSR 服务器。注意：以下是教学用的简化实现，真实生产实现见 react 源码中 react-dom/server 的实现，以及 Next.js 封装后的渲染管线。

    核心原理：两段渲染，一个组件树

    SSR 的全部秘密，就是同一份 React 组件树，被渲染了两次，但两次做的事情完全不同：

    • 服务端第一次：调用 renderToString(<App />)，把组件树"拍扁"成一串纯 HTML 文本。这一阶段只产出标记（Markup），不挂事件、不跑浏览器专有 API。
    • 客户端第二次：浏览器拿到这份 HTML 后，调用 hydrateRoot(container, <App />)，React 不会重新创建 DOM，而是"接管"服务端已经画好的 DOM 节点，把事件监听、状态这些交互能力附加上去。这个附加过程就是水合。
    浏览器请求 /
    →
    服务端取数据
    →
    renderToString
    生成 HTML 字符串
    →
    返回完整 HTML
    (含 <script>)
    →
    浏览器先显示
    再下载 JS
    →
    hydrateRoot
    水合接管
    →
    可交互

    两个关键 API

    服务端渲染与客户端水合的两个入口
    API运行环境作用
    renderToString(element)服务端（Node）把 React 元素树同步渲染成一段 HTML 字符串，只生成标记、不产生交互。它来自 react-dom/server。
    hydrateRoot(container, element)客户端（浏览器）服务端已渲染好标记时使用。复用现有 DOM，只给它挂上事件与状态，不重新铺设 DOM。来自 react-dom/client。

    与之对照，客户端常用的 createRoot(container).render(element) 是"从零创建 DOM"。如果对一份已经由服务端渲染好的 HTML 调用它，React 会先清空容器再重画，白白浪费服务端的工作，还会闪屏。有 SSR 的页面，客户端入口必须用 hydrateRoot，而不是 createRoot。

    最小项目结构

    我们把项目建在 mini-ssr/ 下，结构刻意保持最少：

    mini-ssr 目录结构
    mini-ssr/
├── package.json
├── server.js            # Node http 服务器：SSR 入口
├── src/
│   ├── App.jsx          # 同构组件（服务端、客户端都会渲染它）
│   └── client.js        # 客户端入口：hydrateRoot
└── public/
    └── client.js        # esbuild 打包产物，浏览器加载

    安装依赖只需要四个包：

    mini-ssr/package.json
    {
  "name": "mini-ssr",
  "type": "module",
  "scripts": {
    "build:client": "esbuild src/client.js --bundle --outfile=public/client.js",
    "build:server": "esbuild server.js --bundle --platform=node --outfile=dist/server.cjs",
    "start": "npm run build:client && npm run build:server && node dist/server.cjs"

    这里用 esbuild 做两件事：把带 JSX 的客户端代码打成浏览器能直接跑的 public/client.js；把服务端入口打成 Node 能直接跑的 dist/server.cjs（顺便转译 JSX）。这样运行时就不需要再配 Babel。

    同构组件：同一份代码，跑在两端

    下面这个 App 组件会在服务端被 renderToString 执行一次、在客户端被 hydrateRoot 再执行一次。它同时是纯展示（服务端可渲染）和带交互（客户端可点）的：

    mini-ssr/src/App.jsx
    import { useState } from "react";

// 这份组件同时在服务端（renderToString）和客户端（hydrateRoot）执行。
// 服务端执行时 useState 的初始值会被渲染进 HTML；
// 客户端水合时会复用服务端那份初始值，避免不一致。
export default function App({ initialName }) {
  const [name, setName] = useState(initialName);
  return (
    <main>
      <h1>你好，{name}！</h1>
      <p>这段 HTML 由服务端渲染，按钮由客户端水合后才能点。</p>
      <button onClick={() => setName(name + "·")}>点我加个点</button>
    </main>
  );
}

    注意 App 通过 props 接收 initialName。这个数据是服务端取好、随 HTML 一起注水（Rehydrate）给客户端的，而不是让客户端再请求一次。这就是"数据双端一致"的关键，后面会展开。

    服务端：用 http 模块手写 SSR 响应

    这是本节的核心。服务器做四件事：接收请求 → 取数据 → 调用 renderToString 得到 HTML 字符串 → 拼成完整 HTML 文档返回。浏览器请求的其他路径（如 /client.js）就把打包好的脚本原样吐回去。

    mini-ssr/server.js
    import http from "node:http";
import { readFile } from "node:fs/promises";
import { renderToString } from "react-dom/server";
import React from "react";
import App from "./src/App.jsx";

const PORT = 3000;

// 模拟一次"服务端取数据"。真实项目里这里会查数据库 / 请求接口。
async function fetchInitialData(url) {
  const user = url === "/" ? "世界" : "来访者 " + url;
  return { initialName: user, timestamp: Date.now() };
}

// 把组件树渲染成 HTML 字符串
function renderAppToString(data) {
  return renderToString(React.createElement(App, data));
}

// 拼出完整的 HTML 文档。关键点：
// 1) <div id="root"> 里是服务端渲染好的标记；
// 2) window.__DATA__ 注入注水数据，客户端水合时用；
// 3) 末尾 <script src="/client.js"> 触发水合。
function buildHtml(appHtml, data) {
  return `<!DOCTYPE html>
<html lang="zh-CN">
<body>
  <div id="root">${appHtml}</div>
  <script>window.__DATA__ = ${JSON.stringify(data)};</script>
  <script src="/client.js"></script>
</body>
</html>`;
}

const server = http.createServer(async (req, res) => {
  // 静态资源：直接返回打包好的客户端脚本
  if (req.url === "/client.js") {
    const js = await readFile("./public/client.js");
    res.writeHead(200, { "Content-Type": "text/javascript; charset=utf-8" });
    res.end(js);
    return;
  }

  // 页面请求：走 SSR
  try {
    const data = await fetchInitialData(req.url);
    const appHtml = renderAppToString(data);
    res.writeHead(200, { "Content-Type": "text/html; charset=utf-8" });
    res.end(buildHtml(appHtml, data));
  } catch (err) {
    res.writeHead(500);
    res.end("Internal Server Error: " + err.message);
  }
});

server.listen(PORT, () => console.log("SSR server on http://localhost:" + PORT));

    客户端入口：hydrateRoot 接管已有 DOM

    浏览器侧要做的，只是读取服务端注进来的 window.__DATA__，然后用 hydrateRoot 而不是 createRoot 去挂载同一份 App：

    mini-ssr/src/client.js
    import { hydrateRoot } from "react-dom/client";
import React from "react";
import App from "./App.jsx";

// 与服务端使用完全相同的数据，保证初次渲染输出与 HTML 一致。
const data = window.__DATA__;

hydrateRoot(
  document.getElementById("root"),
  React.createElement(App, data)
);

    到这里一个完整的 SSR 闭环就成立了：

    npm install 安装依赖
    ↓
    npm start：esbuild 打包 client.js 与 server
    ↓
    访问 http://localhost:3000，浏览器先看到服务端 HTML
    ↓
    下载并执行 client.js，hydrateRoot 接管 DOM
    ↓
    按钮可点击，页面成为真正可交互的应用

    你可以自己动手验证：在浏览器"查看网页源代码"里，能看到 <h1>你好，世界！</h1> 这些真实内容（而不是一个空的 <div id="root"></div>）——这就是服务端渲染的标记；而"点我加个点"一开始没反应，直到 client.js 加载完成后才生效——这就是水合。

    静态标记与事件绑定是分离的

    很多人第一次写 SSR 会困惑：HTML 字符串里明明没有 onclick，按钮怎么就活了？答案是：HTML 阶段和交互阶段是分离的两层。

    • HTML 字符串层：renderToString 只输出标签和文本，React 的事件系统并不工作，onClick 在服务端被直接忽略。
    • 水合层：客户端 React 复用了一份"虚拟 DOM 描述"，与服务端输出的真实 DOM 做对照，然后通过事件委托（在根节点上统一监听、再分发到具体组件）把交互挂上去。你写的 onClick 并不对应一个真实的 DOM 属性。

    正因为如此，renderToStaticMarkup（连根节点的 React 水合标记都不输出）适合给邮件、静态页这种"只要内容、不要交互"的场景；一旦页面要交互，就必须用 renderToString 并配合客户端 hydrateRoot。

    常见坑：水合不一致（Hydration Mismatch）›

    水合的前提是"客户端要渲染的内容与服务端那份 HTML 长得一模一样"。一旦不一致，React 就会在控制台报 Hydration Mismatch，轻则打警告、退化到重新渲染，重则整树闪烁。最常见的来源：

    • 服务端和客户端拿到的数据不同——比如客户端用了 new Date()、Math.random()、window.innerWidth，而服务端没有。本例把时间戳放进 data 注水，就是为了让两端一致。
    • 组件在水合前就读取了浏览器专有对象（document、localStorage），而服务端根本没有它们。
    • 前后端对同一文本的序列化结果不同（例如数字精度、日期格式）。

    本演示中如果把 useState(initialName) 改成 useState(Math.random())，立刻就能看到不匹配警告。

    常见坑：数据"双端获取"与注水›

    服务端取一次数据注入 HTML，客户端再自己请求一次，会导致：① 两次请求浪费；② 两端拿到不同时刻的数据，直接引发上面的水合不一致。正确做法就是本例的模式——数据只在服务端取一次，通过 window.__DATA__ 注水给客户端，客户端 hydrate 时复用同一份数据。Next.js 的 App Router 进一步把这件事自动化：服务端组件里直接 await 取数，无需手动注水。

    提示：服务端没有 document/window›

    renderToString 在 Node 里同步执行整个组件树，所以组件渲染期间不能访问任何浏览器专有对象。需要在浏览器环境运行的代码（操作 DOM、监听事件、读取 localStorage），要么放进 useEffect（水合后才执行，服务端会跳过它），要么用动态 import 推迟到客户端。

    最佳实践：和真实框架对照着看›
    1. 先跑通本节这份 60 行的手写 SSR，再去读 Next.js 文档里"服务端渲染"一节，你会发现 Next.js 只是把"拼 HTML 模板、注水数据、打包客户端 bundle、处理缓存"这些脏活全包了。
    2. 用 curl http://localhost:3000 直接看原始响应，确认返回的是完整 HTML（含 <h1>），而不是空壳——这就是 SSR 对搜索引擎（Search Engine Optimization，SEO）友好的根本原因。
    3. 真实环境中 renderToString 是同步的，会阻塞事件循环；Next.js 与生产框架改用流式接口 renderToPipeableStream（见 react-dom/server 文档），这是第 76 节「实现 Streaming」的主题。

    这就是手写 React SSR 的全部核心：服务端 renderToString 出标记，客户端 hydrateRoot 接管制式，数据注水保证两端一致。下一节（第 72 节）我们把"每次请求都实时渲染"改成"构建时预渲染成静态文件 + 运行期缓存更新"，亲手实现 SSG 与 ISR。
