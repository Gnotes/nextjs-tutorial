    从 SSR 到 SSG：把渲染时机提前

    第 71 节的 SSR 服务器，每次请求都要做一次"取数据 → renderToString → 拼 HTML"。如果页面内容其实不常变，这套重复劳动就很浪费。静态站点生成（Static Site Generation，SSG）的思路是：把 renderToString 的调用从"每次请求"挪到"构建时"，提前把每个页面渲染成一个 .html 文件。运行时服务器只负责把这些静态文件读出来返回，根本不再执行 React。

    构建脚本 build.js
    →
    遍历页面路由列表
    →
    每页 renderToString
    得到 HTML 字符串
    →
    写入 dist/xxx.html
    静态文件
    →
    运行时直接返回文件
    不再跑 React

    注意：渲染用的还是上一节同一个 renderToString，变的只是"什么时候、被谁调用"。所以本节代码大量复用第 71 节的组件与模板函数。下面是教学简化实现，真实实现见 Next.js 构建流程与 react-dom/server。

    手写 SSG：build.js 遍历页面并落盘

    我们先定义"有哪些页面"。SSG 必须在构建时就知道全部路由（这正是它和 SSR 的差别之一）。这里用一个路由表 pages 模拟真实项目里的文件约定：

    mini-ssg/build.js
    import { writeFile, mkdir, rm } from "node:fs/promises";
import { renderToString } from "react-dom/server";
import React from "react";
import Page from "./src/Page.jsx";

// 构建期就要枚举出全部静态页面。真实项目里这一步来自文件系统约定
// （如 app/blog/[slug]/page.js 的 generateStaticParams）。
const pages = [
  { path: "index", data: { title: "首页", content: "这是构建时生成的首页。" } },
  { path: "about",  data: { title: "关于", content: "关于我们 —— 同样是构建时渲染。" } },
  { path: "blog/hello", data: { title: "第一篇", content: "你好，SSG！" } },
];

function buildHtml(appHtml) {
  // 与第 71 节几乎一致：注入服务端渲染好的标记 + 客户端水合脚本。
  return `<!DOCTYPE html>
<html lang="zh-CN">
<body>
  <div id="root">${appHtml}</div>
  <script src="/client.js"></script>
</body>
</html>`;
}

async function build() {
  // 清空旧产物
  await rm("dist", { recursive: true, force: true });

  for (const page of pages) {
    const appHtml = renderToString(React.createElement(Page, page.data));
    const html = buildHtml(appHtml);
    // dist/blog/hello/index.html 这种嵌套目录要先建好
    const outDir = "dist/" + page.path;
    await mkdir(outDir, { recursive: true });
    await writeFile(outDir + "/index.html", html, "utf8");
    console.log("已生成: dist/" + page.path + "/index.html");
  }
}

build();

    组件 Page 和第 71 节一样，是同构组件（构建时被 renderToString 渲染，运行时被 hydrateRoot 水合）。构建完成后，dist/ 下就是一堆纯静态 HTML，扔到任何静态托管或内容分发网络（Content Delivery Network，CDN）即可。

    运行 SSG 构建
    # 安装依赖后，构建出静态页面
npx esbuild build.js --bundle --platform=node --outfile=dist-build.cjs
node dist-build.cjs
# 输出：
#   已生成: dist/index/index.html
#   已生成: dist/about/index.html
#   已生成: dist/blog/hello/index.html

# 然后用任意静态服务器托管 dist 目录，例如：
npx serve dist

    SSG 的死穴：内容不新鲜

    SSG 的性能和成本都好，但有个硬伤：内容在构建那一刻就被钉死了。博客发新文章、商品库存变了，都得重新跑一遍 build 再重新部署。页面数量巨大（比如一万个商品详情页）时，全量构建也慢。增量静态再生成（Incremental Static Regeneration，ISR）就是来解决这个的。

    手写 ISR：内存缓存 + revalidate

    ISR 的核心是两句话：① 每个页面缓存一份渲染好的 HTML 和它的"生成时间"；② 请求进来时，如果缓存还在有效期内就直接返回，即使过期了也先把旧的返回给用户，同时在后台悄悄重新生成新的。这就是缓存领域经典的 stale-while-revalidate（过期先用着，后台再校验）语义。

    请求 /blog/hello
    ↓
    查缓存：有没有这份 HTML？
    ↓
    没有 → 同步渲染一份，写入缓存，直接返回
    ↓
    有 → 看 now - 生成时间 是否超过 revalidate 秒数
    ↓
    未过期 → 直接返回旧缓存
    ↓
    已过期 → 立刻返回旧缓存，同时后台异步重新渲染并替换缓存

    注意最后一步：用户拿到的永远是旧页面，后台生成的新页面要等下一次请求才生效。这就是"过期窗口"的由来。下面是完整的 server.js：

    mini-ssg/server.js（ISR 版）
    import http from "node:http";
import { renderToString } from "react-dom/server";
import React from "react";
import Page from "./src/Page.jsx";

const PORT = 3000;
const REVALIDATE = 10; // 秒：页面生成 10 秒后视为过期

// 内存缓存：path -> { html, generatedAt }
const cache = new Map();

// 模拟取数（真实项目里查数据库 / 调接口）
async function fetchData(pathname) {
  return {
    title: pathname,
    content: "生成于 " + new Date().toISOString(),
  };
}

// 渲染并写入缓存
async function renderAndCache(pathname) {
  const data = await fetchData(pathname);
  const html = renderToString(React.createElement(Page, data));
  cache.set(pathname, { html, generatedAt: Date.now() });
  return html;
}

function buildPage(fullHtml) {
  return `<!DOCTYPE html><html><body>
    <div id="root">${fullHtml}</div>
    <script src="/client.js"></script></body></html>`;
}

const server = http.createServer(async (req, res) => {
  const pathname = req.url === "/" ? "index" : req.url.replace(/^\//, "");
  const entry = cache.get(pathname);
  const age = entry ? (Date.now() - entry.generatedAt) / 1000 : Infinity;

  // 1) 缓存没有：同步渲染一份，让这次请求拿到内容
  if (!entry) {
    const html = await renderAndCache(pathname);
    res.writeHead(200, { "Content-Type": "text/html; charset=utf-8" });
    res.end(buildPage(html));
    return;
  }

  // 2) 缓存过期：先返回旧的，后台异步重新生成（stale-while-revalidate）
  if (age >= REVALIDATE) {
    res.setHeader("X-Mini-Cache", "stale, revalidating");
    res.writeHead(200, { "Content-Type": "text/html; charset=utf-8" });
    res.end(buildPage(entry.html));
    // 不 await，后台跑，不阻塞这次响应
    renderAndCache(pathname).catch((e) => console.error("revalidate 失败", e));
    return;
  }

  // 3) 缓存未过期：直接命中
  res.setHeader("X-Mini-Cache", "hit");
  res.writeHead(200, { "Content-Type": "text/html; charset=utf-8" });
  res.end(buildPage(entry.html));
});

server.listen(PORT, () => console.log("ISR server on http://localhost:" + PORT));

    跑起来后可以这样观察行为：连续快速访问同一个路径，响应头是 x-mini-cache: hit；等 10 秒后再访问，第一次响应头变成 stale, revalidating，且页面上的"生成于"时间还是旧的；紧接着再访问，时间才更新、响应头回到 hit。这个"第一次过期请求拿到旧内容、下一次才拿到新内容"的错位，就是 ISR 的全部精髓。

    与第 71 节代码的复用关系

    SSR / SSG / ISR 三段代码复用对照
    部分复用情况差异点
    同构组件 Page / App三段完全共用无——这就是"同构"的意义
    renderToString三段都用它出标记调用时机不同：请求时 / 构建时 / 过期后后台
    buildHtml 模板基本照搬第 71 节注水数据的来源变成缓存里的那一份
    客户端 hydrateRoot 入口三段完全共用无
    缓存层仅 ISR 新增Map 存 html + generatedAt，revalidate 决策

    生成与缓存的取舍

    三种策略在"生成时机 / 运行时成本 / 内容新鲜度"上的权衡
    策略HTML 何时生成运行时还要渲染吗内容新鲜度
    SSR（第 71 节）每次请求实时每个请求都渲染最实时
    SSG（本节 build.js）构建时一次完全不渲染构建时定格，更新要重新 build
    ISR（本节 server.js）构建时 + 过期后后台仅过期时偶尔渲染周期内可能短暂过期
    常见坑：revalidate 不是定时器›

    看上面的代码就能明白：我们没有用 setInterval 去定时刷新。重新渲染只在"过期后有人访问"那一刻才发生。如果一个页面 10 秒就过期了，但一整天没人访问，它就一整天都不会被更新。这与 Next.js 里 fetch(..., { next: { revalidate: 10 } }) 的语义一致——revalidate 是"下次访问时检查"的惰性阈值，不是精确时钟。需要精确时效的场景（秒杀、倒计时）别用 ISR。

    常见坑：过期窗口与并发重复渲染›

    本教学实现有个被刻意简化的点：过期后如果同时来了 10 个请求，会触发 10 次后台 renderAndCache。真实框架（Next.js）会做去重（dedup）：同一时刻同一页面只允许一个在途的重新渲染，其余请求直接用旧缓存。手写时如果要上线，记得给"正在重新生成"的页面加个标志位。另外内存缓存是进程内的，多实例部署时各节点缓存不一致——生产里 Next.js 把缓存放到了文件系统/CDN 层，这超出本节简化范围。

    提示：按需（On-Demand）重新验证›

    除了"定时阈值"，ISR 还支持按需触发：内容一变（比如博客后台点了保存），就调用一次 renderAndCache(pathname) 主动替换缓存，用户立刻看到新内容。Next.js 里对应 revalidatePath() / revalidateTag()。在上面的 server.js 里，只要加一个 POST /revalidate?path=/blog/hello 路由手动调 renderAndCache，就是一个迷你版的按需 ISR。

    最佳实践：观察真实 Next.js 的缓存头›
    1. 本节的 X-Mini-Cache 响应头，对应真实 Next.js 自托管时的 x-nextjs-cache: HIT / STALE / MISS。跑一个默认 Next.js 项目，用 curl -I 多刷几次，观察这三个状态怎么流转，和本节逻辑一一对应。
    2. 手写这两个脚本的目的不是替代框架，而是让你在面试里能说清"ISR 为什么快、为什么会有旧内容窗口"。
