    概念与背景

    Tailwind CSS 是一个实用类优先（Utility-First）的 CSS 框架：它不提供带语义名字的组件类（如 .btn-primary），而是提供大量细粒度的原子类（如 px-4、rounded、bg-blue-500），直接拼在标签上完成样式。它与 Next.js 深度集成——第 18 节已经讲过它在样式体系中的位置，本节聚焦「如何系统地学会它」。

    边界与坑

    核心概念：Utility-First 与设计令牌

    传统写法是「写一个语义类名，再在 CSS 文件里实现样式」；Tailwind 是「直接在标签上组合一堆原子类」。它的类名大多来自一组设计令牌（Design Tokens）——间距、颜色、字号、圆角、阴影的预设尺度：

    任意 TSX 标签
    <button class="rounded bg-blue-500 px-4 py-2 text-sm font-medium text-white">
  保存
</button>
    • px-4 / py-2：水平 / 垂直内边距，4 = 1rem × 0.25 = 1rem。
    • bg-blue-500：背景色，500 是色阶（50 最浅、900 最深）。
    • rounded：圆角；text-sm：字号；font-medium：字重。

    这套尺度是统一的：间距、字号、圆角都从同一套数字刻度取，天然视觉一致，不需要自己凭空调 13px / 17px。

    变体与响应式

    「前缀语法」是 Tailwind 的灵魂：用一个冒号把条件放在类名前面。

    常用前缀（变体）一览
    类别写法含义
    状态变体hover:bg-blue-600
    focus:outline-none    		仅在悬停 / 聚焦时生效，配合键盘可访问性
    响应式断点sm: md: lg: xl:从小到大的断点，默认移动优先（base 类先写）
    深色模式dark:bg-zinc-900跟随系统或 class 切换深色主题
    任意值w-[320px]
    grid-cols-[1fr_2fr]    		方括号里写任意值，不必改配置
    app/page.tsx
    <div class="grid grid-cols-1 gap-4 md:grid-cols-3">
  <div class="rounded-lg bg-white p-4 dark:bg-zinc-800">卡片 1</div>
</div>

    上面的含义：默认单列，从 md（768px）起变三列；卡片背景在深色模式下换成深灰。移动优先意味着：先写小屏生效的 base 类，再用 sm:/md: 叠加大屏规则。

    与 CSS Modules / CSS-in-JS 的对比

    三种样式方案对比
    方案优点缺点
    Tailwind类名即样式、无需切换文件、天然响应式、产物体积小（按需生成）模板里类名很长；不熟悉时像「背单词」
    CSS Modules原生、局部作用域隔离、语义类名要维护单独的 .module.css 文件，响应式要手写媒体查询
    CSS-in-JS样式与组件同处一处、动态值方便运行时开销、打包体积、与 RSC 生态兼容差

    在 React Server Components (RSC) 成为默认后，很多运行时 CSS-in-JS 库需要额外配置才能工作，而 Tailwind 是编译期生成静态 CSS，天然与服务端组件兼容——这是它在 Next.js 生态里流行的重要原因。

    配置与组件化提取

    当默认令牌不够用时，在 tailwind.config.ts 里用 theme.extend 扩展（而不是覆盖）：

    tailwind.config.ts
    import type { Config } from "tailwindcss";

export default {
  content: [
    // 告诉 Tailwind 扫描哪些文件里出现了类名，只生成用到的 CSS
    "./app/**/*.{ts,tsx}",
    "./components/**/*.{ts,tsx}",
  ],
  theme: {
    extend: {
      colors: {
        brand: "#0ea5e9", // 新增一个品牌色
      },
    },
  },
} satisfies Config;
    常见坑：content 漏写路径导致样式「消失」›

    Tailwind 是按需生成：它扫描 content 里列出的文件，发现哪些类名真的被用到，才生成对应 CSS。如果你新建了 widgets/ 目录却没加进 content，那里的类名会被当作「未使用」而不生成 CSS，页面就像没样式一样。改完目录结构务必同步检查 content。

    当一组类在多处复用，可以用 @apply 抽到 CSS 里（如做一个 .btn-primary），但官方建议克制使用：过度 @apply 等于又回到了写自定义 CSS 的老路，失去 utility-first 的灵活性。更常见的做法是提取成一个 React 组件（见第 64 节 shadcn/ui 的思路）。

    与 Next.js 集成注意点

    • 全局样式入口：在根 app/layout.tsx 里 import 一次全局 CSS（含 @tailwind 指令或 Tailwind v4 的 @import "tailwindcss"）。
    • RSC 里 className 动态拼接：在服务端组件里拼接类名没有运行时问题，但如果用了「只有运行时才知道是否存在的类名字符串」，那些类名不会出现在静态扫描里，从而不被生成。结论：动态拼接的类名必须保证完整字面量出现在代码中，而不是把 text- 和颜色拆开再拼。
    components/Badge.tsx
    // 推荐：用对象映射，key 是完整类名字面量，扫描器能识别
const tones = {
  red: "bg-red-100 text-red-700",
  green: "bg-green-100 text-green-700",
};

export function Badge({ tone, children }: { tone: "red" | "green"; children: React.ReactNode }) {
  return <span className={`rounded-full px-2 py-0.5 text-xs ${tones[tone]}`}>{children}</span>;
}
    反例：把类名拆开拼接›

    `text-${color}-700` 这种写法，扫描器在源码里只能看到 text-、700，拼不出完整类名，对应 CSS 永远不会被生成。永远写完整的类名字面量（哪怕冗余）。

    学习计划（建议节奏）

    1. 第 1 周：在 Tailwind 官方 Docs 的「Core Concepts」里把 Layout / Spacing / Sizing / Colors / Typography 五类过一遍，边看边在 playground 里写。
    2. 第 2 周：专攻状态变体与响应式（Hover / Focus / Breakpoints / Dark Mode），把一个普通页面改造成响应式 + 暗色。
    3. 第 3 周：学习 tailwind.config 的 theme.extend、任意值语法、与 Next.js 的接入。
    4. 第 4 周：用第 62 节 Storybook 把组件做成可交互文档，或直接上手第 64 节 shadcn/ui（它本身就是 Tailwind 的最佳实践封装）。
    最佳实践：先记「刻度」再查「细节」›

    不要试图背下所有类名。真正要记的是：数字刻度（0,0.5,1,2,3,4...）、色阶（50-900）、断点（sm/md/lg/xl）和变体冒号语法。具体某个属性叫什么，随时查官方文档的搜索框即可——这正是 utility-first 的学习方式。
