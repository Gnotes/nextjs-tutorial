    概念与背景

    前面的章节按「路由 → 渲染 → 数据 → 缓存 → 组件 → 配置」把 Next.js 的能力拆开讲了一遍。本节把它们收束成一份可落地的最佳实践清单：官方在 Building Your Application 与 API Reference 之外，还维护了一组「Do / Don't」式的指导（如数据获取、缓存、性能、安全、可访问性）。本节按七个维度分类组织，每类给出原则、常见反模式与官方对应文档链接。

    一个总纲：能在服务端做的事就不要搬到客户端。React Server Components (RSC) 让组件默认跑在服务端，天然减少需要水合（Hydration）、下发到浏览器的 JavaScript 体积；把交互性最小化地切成客户端组件，是 Next.js 性能与可维护性的第一性原理。

    路由与组件

    App Router 的心智是「以文件夹为路由、以文件为约定」。目录里的 page.tsx、layout.tsx、loading.tsx、error.tsx 分别对应页面、布局、加载态与错误态。

    路由与组件的最佳实践
    主题推荐做法要避免的反模式
    组件边界默认写服务端组件；只在需要事件、状态、浏览器 API 时才加 "use client"整页加 "use client"，把整个页面从服务端渲染里拖出来
    组合模式用 layout 的 props.children 做嵌套，把公共导航/侧边栏提升到上层布局在每个页面里重复 import 同一套外壳
    路由组织用路由组（(group)）按业务分目录，用 _folder 放非路由模块把工具函数、类型、测试文件散落在 app 路由目录里
    导航用 <Link> 做客户端导航，避免 <a> 整页刷新在 RSC 里直接调用 useRouter()（它是客户端 Hook）
    最佳实践：按「交互需求」决定组件类型›

    判断一个组件要不要加 "use client"，只看它是否用到：事件处理（onClick）、状态（useState）、浏览器 API（window）、或客户端专属 Hook。都不需要，就保持服务端组件。把交互拆成最小的叶子组件（如一个 <ThemeToggle />），其余外壳仍留在服务端。

    数据获取与缓存

    App Router 推荐在服务端组件里直接 async/await 取数，由框架自动处理缓存与去重，而不是在客户端用 useEffect + 状态。

    app/posts/page.tsx
    // 推荐：服务端组件里直接 await，自动缓存、自动去重
async function getPosts() {
  const res = await fetch("https://api.example.com/posts", {
    next: { revalidate: 60 }, // 每 60 秒重新验证一次缓存
  });
  if (!res.ok) throw new Error("Failed to fetch posts");
  return res.json();
}

export default async function PostsPage() {
  const posts = await getPosts();
  return <ul>{posts.map((p) => <li key={p.id}>{p.title}</li>)}</ul>;
}
    数据获取要点
    要点说明
    服务端取数优先数据请求放在服务端组件，避免向浏览器暴露内部地址与密钥，也避免首屏加载后再发请求的「双跳」。
    并行取数消除瀑布多个相互独立的请求用 Promise.all 同时发起，而不是依次 await，减少串行等待。
    用 revalidate 控新鲜度通过 fetch 的 next.revalidate 或 revalidateTag 控制增量静态再生成（Incremental Static Regeneration，ISR）周期。
    敏感操作走 Server Actions写操作、表单提交优先用 Server Actions，服务端直接拿到鉴权后的用户上下文，不必自建接口。
    常见坑：客户端数据请求瀑布›

    在服务端组件里依次 await a(); await b(); 是常见的性能陷阱：两个独立请求本可并行，却被串行化。官方建议用 Promise.all 或「在渲染前就并行触发」的方式消除瀑布。反过来，客户端用 useEffect 取数还会产生「先渲染空壳 → 再请求 → 再渲染」的二次闪烁。

    性能优化

    Next.js 对常用性能手段做了一等支持，优先用官方组件与约定，而不是手写裸标签。

    性能优化清单
    方向做法对应章节
    图片用 next/image 的 <Image>，自动格式转换、尺寸占位、懒加载第 21 节 Images
    字体用 next/font 自托管字体，避免第三方请求与布局偏移第 22 节 Font
    懒加载用 next/dynamic 按需加载重组件与第三方库第 26 节 懒加载

    代码分割按路由自动分包，配合动态 import 进一步切分大包官方 Code Splitting 文档

    无障碍（Accessibility）

    无障碍不仅是合规要求，也改善搜索引擎优化（Search Engine Optimization，SEO）与键盘用户体验。官方在 Accessibility 指南中给出可操作清单：

    • 每个页面有唯一的 <h1>，标题层级按顺序递进。
    • 图片提供有意义的 alt；装饰性图片用空 alt=""。
    • 表单控件带 <label>，错误信息与字段关联（aria-describedby）。
    • 交互元素可被 Tab 聚焦，焦点状态可见（本模板用 :focus-visible）。
    • 用 ESLint 的 eslint-plugin-jsx-a11y 自动拦截常见违规。

    安全

    安全基线
    方向做法
    内容安全策略配置 Content Security Policy（CSP）限制脚本来源，第 31 节专门讲草稿模式与 CSP。
    认证与授权用成熟方案（如第 60 节 Clerk、或 next-auth）做登录；服务端取数前先校验 auth()，不要信任客户端传来的身份。
    环境变量密钥放服务端变量（.env）；只有加 NEXT_PUBLIC_ 前缀的才会下发到浏览器。
    依赖安全定期 npm audit，锁定依赖版本，谨慎引入小众包。
    输入校验所有外部输入（表单、URL 参数、请求体）用 Zod 等库校验（第 63 节）。

    测试

    官方推荐两层测试组合：Vitest（或 Jest）跑单元 / 组件测试，Playwright 跑端到端（End-to-End，E2E）测试。

    终端（官方测试指南示例）
    # 官方示例仓库提供的测试脚手架
npx vitest run            # 单元 / 组件测试
npx playwright test       # 端到端测试
    • 对工具函数、校验逻辑、组件渲染写单元测试（Vitest）。
    • 对核心用户旅程（登录、下单、支付）写 E2E（Playwright），跑在真实浏览器里。
    • 官方 Testing 指南 提供了从零配置 Vitest 与 Playwright 的步骤。

    可维护性

    • 目录约定：业务代码放 app/，可复用组件放 components/，工具函数放 lib/ 或 utils/，用路径别名 @/ 引入（第 19 节）。
    • TypeScript 严格模式：开启 strict，让编译器帮你挡住空值与类型错误（第 29 节）。
    • 统一环境变量：在 .env.example 里登记所有变量及含义，新成员 clone 后照填即可。
    • ESLint + Prettier：提交前自动格式化与检查，减少风格争论。
    提示：把这份清单当作 Code Review 检查表›

    建议把本节的表格复制进团队的 Code Review 模板：每个 PR 至少过一遍「组件边界 / 取数位置 / 性能组件 / 安全 / 测试」五项。最佳实践的价值不在记住，而在养成默认习惯。
