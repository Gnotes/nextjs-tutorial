    概念与背景

    搜索引擎优化（Search Engine Optimization，SEO）的目标是让博客文章能被搜索引擎正确抓取、理解并排在结果里。Next.js 对 SEO 天然友好：静态站点生成（Static Site Generation，SSG）产出的是服务端渲染好的 HTML，爬虫无需执行 JavaScript 就能读到正文——这正是第 51 节选择 SSG 的原因。但"页面静态"只是基础，还需要补齐四样东西：

    • 页面元信息：标题、描述、规范链接（canonical）、社交分享卡片（OG）。
    • 站点地图：告诉爬虫有哪些 URL 可以抓取（sitemap.xml）。
    • 抓取规则：用 robots.txt 圈定可抓范围。
    • 结构化数据：用 JavaScript 对象表示法（JavaScript Object Notation，JSON）的 LD（Linked Data）格式告诉搜索引擎"这是一篇文章、作者是谁、何时发布"。

    用 Metadata API 落地

    第 24/25 节讲过 Metadata：在根布局设置全站默认值与标题模板，再在文章详情页用 generateMetadata 按文章动态生成。假设博客域名为 https://www.myblog.dev。

    app/layout.tsx
    import type { Metadata } from "next";

export const metadata: Metadata = {
  metadataBase: new URL("https://www.myblog.dev"),
  title: {
    // 模板：子页标题会拼成 "你好，世界 | my-blog"
    default: "my-blog",
    template: "%s | my-blog",
  },
  description: "一个用 Next.js 搭建的技术博客。",
};

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN">
      <body>{children}</body>
    </html>
  );
}
    app/blog/[slug]/page.tsx（generateMetadata 部分）
    import type { Metadata } from "next";
import { getPost } from "@/lib/posts";

export async function generateMetadata({
  params,
}: {
  params: Promise<{ slug: string }>;
}): Promise<Metadata> {
  const { slug } = await params;
  const post = await getPost(slug);
  if (!post) return {};
  return {
    title: post.title,                 // 经模板拼成 "标题 | my-blog"
    description: post.description,
    alternates: { canonical: `/blog/${slug}` },  // 规范链接，避免重复内容
    openGraph: {
      type: "article",
      title: post.title,
      description: post.description,
      url: `/blog/${slug}`,
      publishedTime: post.date,
      tags: post.tags,
    },
  };
}

    sitemap 与 robots

    Next.js 提供基于文件约定的元数据文件：在 app/ 下建 sitemap.ts 与 robots.ts，构建时自动产出 /sitemap.xml 与 /robots.txt。sitemap 里要列出所有文章 URL。

    app/sitemap.ts
    import { getSortedPosts } from "@/lib/posts";

export default function sitemap() {
  const base = "https://www.myblog.dev";
  const posts = getSortedPosts().map((p) => ({
    url: `${base}/blog/${p.slug}`,
    lastModified: new Date(p.date),
  }));
  return [
    { url: base },
    { url: `${base}/blog` },
    ...posts,
  ];
}
    app/robots.ts
    import type { MetadataRoute } from "next";

export default function robots(): MetadataRoute.Robots {
  return {
    rules: { userAgent: "*", allow: "/" },
    sitemap: "https://www.myblog.dev/sitemap.xml",
  };
}

    结构化数据 JSON-LD

    结构化数据让搜索引擎把页面内容理解成"一篇 Article"，有机会展示富媒体摘要。做法是在文章页注入一段 application/ld+json 脚本。它属于服务端渲染内容，放在组件里即可。

    app/blog/[slug]/page.tsx（注入 JSON-LD）
    // 在 PostPage 组件返回值里，正文之外加一段结构化数据
export default async function PostPage({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const post = (await getPost(slug))!;

  const jsonLd = {
    "@context": "https://schema.org",
    "@type": "Article",
    headline: post.title,
    description: post.description,
    datePublished: post.date,
    author: { "@type": "Person", name: "my-blog" },
  };

  return (
    <article>
      {/* 注入结构化数据 */}
      <script
        type="application/ld+json"
        dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }}
      />
      <h1>{post.title}</h1>
      <div dangerouslySetInnerHTML={{ __html: post.contentHtml }} />
    </article>
  );
}

    next-seo 与手写 Metadata 的取舍

    SEO 方案对比
    方案优点缺点
    Next.js 原生 Metadata API零依赖、与框架同构、自动处理 head写 JSON-LD 等需手动拼对象
    next-seo封装好的 NextSeo 组件，开箱即用主要面向 Pages Router；App Router 下官方建议用原生 Metadata

    结论：App Router 项目优先用原生 Metadata API，不必为 SEO 再引入 next-seo；它在 Pages Router 项目里仍是常见选择。

    核心网页指标与 SEO

    Google 把页面体验纳入排名信号，其中核心网页指标（Core Web Vitals，CWV）是关键项。它衡量的是"快不快、稳不稳、卡不卡"：

    指标含义博客里常见优化点
    LCP最大内容绘制（Largest Contentful Paint），主内容多久出现静态页面、字体/图片优化、减少阻塞脚本
    FCP首次内容绘制（First Contentful Paint），首屏多久有内容SSG 直出 HTML，天然占优
    CLS累积布局偏移（Cumulative Layout Shift），页面元素意外跳动图片写宽高、预留占位
    INP交互到下一次绘制（Interaction to Next Paint），响应是否跟手控制客户端 JS 体积（见第 56 节）
    SSG + Metadata + sitemap 这套组合，本质上就是把"可抓取、可理解、体验好"三件事一次性做完。第 56 节会用 next build 与 bundle-analyzer 继续优化体积，进一步改善 LCP / INP。
    常见坑›
    • metadataBase 不设置，相对路径的 openGraph.url 在部署后可能解析失败，社交分享卡片打不开。
    • 同一篇文章若同时有 /blog/xxx 和带参数的副本，务必用 alternates.canonical 指一个规范地址，否则会被判定重复内容。
    • JSON-LD 里的 @context 必须是 https://schema.org，字段名按规范写，不要自创。
    最佳实践›
    • 标题模板统一在根 layout 配一次，子页只写短标题，避免每个页面手拼。
    • 写完用 Google 的富媒体测试（Rich Results Test）校验 JSON-LD 是否被识别。
    • 文章 URL 一经发布不要变；变了就加 301 重定向并更新 sitemap。
