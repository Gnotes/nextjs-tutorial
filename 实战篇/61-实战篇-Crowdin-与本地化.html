    概念与背景

    国际化（internationalization，i18n）做到一定阶段都会撞上同一个问题：翻译的协作与维护。开发者把字符串散在 messages/en.json、messages/zh.json 里，然后呢？谁来翻译？怎么避免新旧字符串对不上？怎么利用上一次翻译过的句子？Crowdin 就是为这件事而生的云端翻译管理平台（Translation Management System，TMS）。

    它的核心思路是：开发者只管维护一份「源语言」字符串，把它推到 Crowdin；翻译（人工、众包、或机器翻译）在 Crowdin 的网页界面里完成；翻译好的结果再被拉回仓库。过程中 Crowdin 自动积累翻译记忆（Translation Memory，TM）与术语库（Glossary），重复句子只翻一次，术语前后一致。

    仓库 messages/en.json
    源语言字符串
    →
    上传到 Crowdin
    （CLI / GitHub App）
    →
    翻译 + 审校
    （人工 / 机器）
    →
    拉回 translations
    生成 zh/ja/…
    →
    构建部署上线

    它解决了哪些手译的痛点

    手翻 messages 文件 vs Crowdin
    痛点纯手翻的做法Crowdin 的做法
    译者不懂代码把 JSON 文件发给译者，容易改坏格式网页编辑器里只看到「键 + 原文 + 译文」，碰不到代码
    重复句子重复翻每次新文件都从头翻翻译记忆自动提示「这句翻过了」
    术语不统一不同译者把同一个词翻成不同说法术语库强制统一
    新旧键对不上新增键忘了补其他语言，运行时 fallback界面里标出哪些键「缺翻译 / 待审校」
    流程自动化手动拉取翻译再提 PRGitHub App / CLI 在 CI 里自动同步

    本地化工作流：从源码字符串到翻译回仓

    以第 55 节博客 i18n 项目为例，假设你已经用 next-intl（或类似库）把文案抽到了消息文件里。接入 Crowdin 后，日常迭代变成下面这条流水线。

    第一步：确定「源文件」与「翻译文件」的映射

    在项目根放一个 crowdin.yml，告诉 Crowdin 哪个文件是源、翻译结果输出到哪里、支持哪些目标语言。

    crowdin.yml
    project_id_env: CROWDIN_PROJECT_ID
api_token_env: CROWDIN_PERSONAL_TOKEN

files:
  - source: /messages/en.json        # 源语言（英语）
    translation: /messages/%two_letters_code%.json  # 输出为 zh.json / ja.json …
    languages_mapping:
      two_letters_code:
        zh-CN: zh
        ja: ja
    注意：语言代码映射›

    Crowdin 内部用「zh-CN、zh-TW」这类标准区域码，而你的项目可能习惯用「zh」。languages_mapping 就是把两边对齐的地方，避免拉回时生成出一堆命名不一致的文件。

    第二步：上传源字符串、拉取翻译（CLI）

    Crowdin 官方命令行工具（Command-Line Interface，CLI）是 @crowdin/cli，两条核心命令：upload 把本地源文件推上去，download 把审校过的译文拉回来。

    终端
    # 安装（全局或本地 devDependencies 均可）
npm i -g @crowdin/cli

# 把 messages/en.json 的新内容上传到 Crowdin
crowdin upload sources

# 把审校完成的译文下载回 messages/ 目录
crowdin download

    这两条命令通常不手动跑，而是接进持续集成 / 持续部署（Continuous Integration / Continuous Delivery，CI/CD）：开发者改完 en.json 提交，CI 自动 upload；译完后自动 download 并提一个「更新翻译」的合并请求（Pull Request，PR）。

    第三步：GitHub 集成（免写脚本）

    不想维护 CI 脚本时，直接在 GitHub 安装 Crowdin GitHub App 并关联仓库：之后每次源文件变更自动同步，翻译完成后 Crowdin 自动开 PR 把译文送回仓库。这对开源项目尤其友好——开源项目还能享受 Crowdin 的免费开源计划，并方便贡献者直接在网页里参与翻译（众包翻译）。

    与 next-intl / i18n 的配合

    Crowdin 只负责「翻译文件的生产与流转」，运行时用哪套 i18n 库是另一层。常见组合是：

    • 开发态：你维护 messages/en.json（源），代码里用 next-intl 的 useTranslations() 取文案。
    • 翻译态：Crowdin 基于 en.json 产出 zh.json、ja.json 等。
    • 运行态：next-intl 按当前 locale 加载对应文件，开发者完全不用碰翻译内容。
    app/[locale]/page.tsx（next-intl 消费侧，节选）
    import { useTranslations } from "next-intl";

export default function Home() {
  const t = useTranslations("Home"); // 对应 messages/*.json 里的 "Home" 命名空间
  return <h1>{t("title")}</h1>; // Crowdin 只负责让 zh.json 里的 title 有译文
}

    QA 与审校

    Crowdin 界面内建了翻译质量检查：未翻译的字符串、占位符（如 {name}）在译文中是否被保留、术语一致性、超长截断风险。正式上线前，建议至少过一道「审校（Approval）」流程——译者提交，审校者确认，只有被审校的字符串才 download 回仓库。

    常见坑：占位符与 ICU plural 别被译坏›

    "welcome": "你好，{name}" 里的 {name} 是变量占位符，译者不能翻译它，否则运行时直接报错。同样，ICU 复数语法 {count, plural, ...} 是结构化标记。Crowdin 会用引号保护这些片段，但你仍应在术语库里把它们标注为「勿译」，并在 QA 里检查。

    最佳实践：把 Crowdin 当作「翻译的单一事实源」›

    约定一条铁律：除英语源文件外，其他语言的 messages 文件只由 Crowdin 生成，不手写。这样避免「仓库里手改了 zh.json、下次 download 又被覆盖」的冲突。新增文案只改 en.json，其余交给流水线。
