Contentlayer 是一个"内容层（Content Layer）"工具：把仓库里的 Markdown / MDX 文件编译成类型安全的 JSON 数据，组件里直接 import 就能拿到带类型的文章。本节讲清它的配置与用法，同时如实说明官方已停止维护，并给出 velite、content-collections 等替代方案。

本节目录

    概念与背景

    第 51 节我们手写了 lib/posts.ts：用 fs.readdirSync 读目录、用 gray-matter 拆 frontmatter。它能用，但有三个痛点：frontmatter 字段没有类型约束（少写一个 date 编译期不会报错）、排序与取数逻辑要手写、MDX 渲染要自己接插件链。

    Contentlayer 把这层重复劳动抽成一个"内容层"：你在一个 contentlayer.config.ts 里声明文章的"文档类型（Document Type）"和字段结构，它在开发/构建时监听 content/ 目录，把每个 .md / .mdx 编译成带类型的 JavaScript 模块，输出到 .contentlayer/generated/。组件里 import { allPosts } from "contentlayer/generated" 即可，字段全部有 TypeScript 类型提示。

    核心 API

    Contentlayer 常用函数
    API作用
    defineDocumentType定义一种文档集合，如 Post，声明其 frontmatter 字段名、类型与是否必填。
    defineNestedType定义文档内部嵌套的子结构类型（如作者对象、标签数组）。
    makeSource创建数据源，挂载上面定义的文档类型，并指定读取的文件目录与 MDX 插件链。
    computedFields在编译期由已有字段派生新字段（如由 slug 算出 url = `/blog/${slug}`）。

    配置 contentlayer.config.ts

    contentlayer.config.ts
    import { defineDocumentType, makeSource } from "contentlayer/source-files";

// 定义文章文档类型：声明 frontmatter 有哪些字段
export const Post = defineDocumentType(() => ({
  name: "Post",
  // 匹配 content/posts 下所有 .md / .mdx 文件
  filePathPattern: `posts/**/*.mdx`,
  contentType: "mdx",
  fields: {
    title: { type: "string", required: true },
    date: { type: "date", required: true },
    description: { type: "string", required: false },
    tags: { type: "list", of: { type: "string" }, default: [] },
  },
  // 派生字段：自动算出每篇文章的访问路径
  computedFields: {
    url: {
      type: "string",
      resolve: (post) => `/blog/${post._raw.flattenedPath.replace("posts/", "")}`,
    },
  },
}));

export default makeSource({
  contentDirPath: "content",
  documentTypes: [Post],
});

    与 Next.js 集成

    安装依赖后，需要让 Next.js 的构建管线先跑 Contentlayer。分三步：装包、包装 next.config、补一条开发脚本。

    终端
    npm install contentlayer next-contentlayer
    next.config.mjs
    import { withContentlayer } from "next-contentlayer";

/** @type {import('next').NextConfig} */
export default withContentlayer({
  // 你的其他 Next.js 配置保持不变
});
    package.json（scripts 片段）
    {
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    // 开发时并行跑 contentlayer 的文件监听
    "postinstall": "contentlayer build"
  }
}

    在页面里读取数据与渲染

    集成完成后，文章就变成了从 contentlayer/generated 导出的带类型数据。列表页直接 allPosts，详情页用 Contentlayer 提供的 Post 类型与 MDXContent 渲染正文。

    app/blog/page.tsx（基于 Contentlayer）
    import Link from "next/link";
import { allPosts } from "contentlayer/generated";

export default function BlogIndexPage() {
  // allPosts 是带类型的数组，按日期倒序
  const posts = allPosts.sort(
    (a, b) => a.date < b.date ? 1 : -1
  );
  return (
    <main className="mx-auto max-w-2xl px-6 py-16">
      <h1 className="text-3xl font-bold">博客文章</h1>
      <ul className="mt-8 space-y-6">
        {posts.map((p) => (
          <li key={p.url}>
            <Link href={p.url} className="hover:underline">
              <span className="text-xl font-semibold">{p.title}</span>
            </Link>
            <p className="text-sm text-gray-500">{p.date}</p>
            <p className="mt-1">{p.description}</p>
          </li>
        ))}
      </ul>
    </main>
  );
}
    app/blog/[slug]/page.tsx（基于 Contentlayer）
    import { allPosts } from "contentlayer/generated";
import { useMDXComponent } from "next-contentlayer/hooks";

// 每个 slug 对应一篇文章，构建时静态生成
export function generateStaticParams() {
  return allPosts.map((p) => ({ slug: p._raw.flattenedPath.replace("posts/", "") }));
}

export async function generateMetadata({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const post = allPosts.find(
    (p) => p._raw.flattenedPath === `posts/${slug}`
  );
  return { title: post?.title, description: post?.description };
}

// 用 MDX 组件渲染器渲染单篇文章正文
function Mdx({ code }: { code: string }) {
  const Component = useMDXComponent(code);
  return <Component />;
}

export default async function PostPage({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const post = allPosts.find(
    (p) => p._raw.flattenedPath === `posts/${slug}`
  );
  if (!post) return <p>文章不存在</p>;
  return (
    <article className="mx-auto max-w-2xl px-6 py-16">
      <h1 className="text-3xl font-bold">{post.title}</h1>
      <Mdx code={post.body.code} />
    </article>
  );
}
    重要：Contentlayer 官方已停止维护›

    在你的项目里引入 Contentlayer 前必须知道：Contentlayer 官方仓库（contentlayerdev/contentlayer）已在 README 顶部声明——"Unfortunately Contentlayer is no longer maintained due to lack of funding"（因缺乏资金，项目不再维护），仓库随后被归档（archived）。这意味着它不会再适配未来的 Next.js / React 版本，遇到新框架的兼容性问题官方不会再修。历史上它与 Next.js 13+ App Router、新 MDX 版本的兼容问题一直较多。学习它的"内容层"思想很有价值，但新项目不建议直接采用。

    替代方案对比

    Contentlayer 与主流替代方案
    方案特点适用建议
    Contentlayer类型安全、API 优雅；已停止维护存量项目维护；新项目不推荐
    Velite用 Zod schema 校验、自动生成 TS 类型、轻量快速、框架无关，被社区视为"事实上的继任者"新项目首选替代
    content-collections把内容编译成类型安全的数据集合，提供 Next.js / Remix 集成偏好"内容集合"模型时使用
    MDX 直读第 51 节手写的 fs + gray-matter + remark，零额外抽象内容量小、想完全可控时
    最佳实践›
    • 理解"内容层"这个思想比记住具体 API 更重要：把内容文件编译成类型安全数据、与组件解耦，这是 Velite / content-collections 共同的思路。
    • 若你只是想给博客加类型，直接用 Velite 的 Zod 声明字段即可，不必背负一个已归档的依赖。
    • 文章源目录统一放在 content/，这样将来从 Contentlayer 迁到 Velite 时，文章文件本身一行都不用动。
