    概念与背景

    TypeScript 给了你「编译时」的类型，但到了运行时——接收一个 HTTP 请求体、读一个环境变量、解析表单——数据其实是不受控的：网络对面传来什么就是什么，类型在运行时并不存在。Zod 是一个「TypeScript 优先（TypeScript-first）」的 schema 声明与校验库：你用它定义一份数据「形状」，它既能在运行时校验数据合不合法，又能反推出对应的 TypeScript 类型，让「运行时校验」和「静态类型」始终保持一致，不必手写两遍。

    定义 schema
    z.object({...})
    →
    运行时校验
    .parse(data)
    →
    自动推导类型
    z.infer
    →
    类型与校验
    永远一致

    基础 API：从声明到校验

    终端
    npm install zod
    lib/schema.ts
    import { z } from "zod";

// 1) 用 Zod 的类型构造器描述数据形状
const UserSchema = z.object({
  name: z.string().min(2),
  email: z.string().email(),
  age: z.number().int().positive().optional(), // 可选
  tags: z.array(z.string()).default([]),
});

// 2) z.infer 从 schema 反推 TypeScript 类型 —— 只写一次，两边同步
type User = z.infer<typeof UserSchema>;
//   = { name: string; email: string; age?: number; tags: string[] }
    常用类型与链式方法
    写法含义
    z.string() / z.number() / z.boolean()基本类型
    .email() / .min(n) / .max(n)字符串格式与长度约束
    z.object({...})对象，逐字段约束
    z.array(z.string()) / z.enum(["a","b"])数组 / 枚举
    .optional() / .default(x) / .nullable()可选 / 默认值 / 可空
    z.union([...]) / .or(...)联合类型

    parse 与 safeParse：两种错误处理姿势

    lib/parse.ts
    // A) .parse：校验失败直接抛异常，适合「数据不该错」的内部场景
const user = UserSchema.parse({ name: "A", email: "bad-email" }); // 抛 ZodError

// B) .safeParse：不抛异常，返回 { success, data, error }，
//    适合用户输入 / 不可信数据 —— 你想优雅地展示错误而不是崩掉
const result = UserSchema.safeParse({ name: "A", email: "bad-email" });
if (!result.success) {
  console.log(result.error.issues); // 每个字段的错误信息
} else {
  const ok = result.data; // 类型是 User
}
    选择依据：什么时候用 safeParse›

    凡是「外部输入」——表单、HTTP 请求体、第三方 Webhook、环境变量——都用 safeParse，把错误转成对用户友好的提示。parse 只在你「确定数据应当合法、错了就是程序 bug」的内部数据上用，让异常尽快暴露。

    场景一：API 请求体校验（Route Handler / Server Action）

    这是 Next.js 里最常见的落点：客户端发来的 POST 数据，先过一道 Zod，再进业务逻辑。

    app/api/posts/route.ts
    import { NextResponse } from "next/server";
import { z } from "zod";

const CreatePostSchema = z.object({
  title: z.string().min(1, "标题不能为空").max(80),
  content: z.string().min(10),
});

export async function POST(req: Request) {
  const body = await req.json();
  const parsed = CreatePostSchema.safeParse(body);

  if (!parsed.success) {
    // 把字段级错误整理成 400 返回
    return NextResponse.json({ error: parsed.error.flatten().fieldErrors }, { status: 400 });
  }

  const { title, content } = parsed.data; // 此处类型安全
  // ... 写入数据库（伪代码）
  return NextResponse.json({ ok: true, title });
}

    在 Server Action 里写法同理：safeParse 失败就把错误连同表单一起返回给用户。

    场景二：表单校验（配合 React Hook Form）

    React Hook Form（第 65 节专门讲）有一个 zodResolver，让你把同一套 Zod schema 直接当作表单校验规则，省去手写校验逻辑。

    components/SignupForm.tsx
    "use client";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { z } from "zod";

const SignupSchema = z.object({
  email: z.string().email("邮箱格式不对"),
  password: z.string().min(8, "密码至少 8 位"),
});
type SignupInput = z.infer<typeof SignupSchema>;

export function SignupForm() {
  const { register, handleSubmit, formState: { errors } } =
    useForm<SignupInput>({ resolver: zodResolver(SignupSchema) });

  return (
    <form onSubmit={handleSubmit((data) => console.log(data))}>
      <input {...register("email")} placeholder="邮箱" />
      {errors.email && <p>{errors.email.message}</p>}
      <input type="password" {...register("password")} placeholder="密码" />
      {errors.password && <p>{errors.password.message}</p>}
      <button type="submit">注册</button>
    </form>
  );
}

    场景三：环境变量校验（呼应第 19 节）

    环境变量在运行时是字符串，且可能缺失。启动时用 Zod 校验一次，能把「部署后才发现少配了 DATABASE_URL」的问题提前到启动瞬间。

    lib/env.ts
    import { z } from "zod";

const EnvSchema = z.object({
  DATABASE_URL: z.string().url(),
  NEXT_PUBLIC_API_URL: z.string().url(),
  // 布尔类环境变量常是字符串，用 transform 转成真布尔
  ENABLE_ANALYTICS: z.string().transform((v) => v === "true"),
});

const parsed = EnvSchema.safeParse(process.env);
if (!parsed.success) {
  // 启动即失败，并明确指出缺了哪个变量
  throw new Error("环境变量配置错误: " + JSON.stringify(parsed.error.flatten().fieldErrors));
}

export const env = parsed.data; // 之后全项目用 env.DATABASE_URL，类型安全
    常见坑：把「运行时校验」和「类型断言」混为一谈›

    不要写 const user = data as User 然后假装类型安全——as 只是骗过编译器，运行时数据该错还是错。Zod 的意义在于真的去检查。此外注意 NEXT_PUBLIC_ 变量会被打包进浏览器，别把密钥放进去校验，密钥只能在服务端读取。

    最佳实践：一份 schema，多处复用›

    把同一个 schema 用在「前端表单校验 + 后端请求体校验」两处：前端 zodResolver 给即时反馈，后端 safeParse 做兜底。这样前端校验被绕过（直接 curl 接口）时，后端仍然拦住非法数据——不要相信前端校验。
