实战篇 | Clerk 与登录注册

    概念与背景

    登录注册看似简单，真做起来要操心的事很多：邮箱验证码、第三方登录（Google、GitHub）、密码重置、多因素认证（Multi-Factor Authentication，MFA）、会话管理、用户后台、账号删除合规……Clerk 把这一整套做成了一个托管的全栈认证平台：前端有现成的登录/注册组件，后端有用户数据与 Webhook，开发者几乎不用自己存密码、不用手写会话。

    与第 44 节介绍的 next-auth（开源、自托管、需要自己接数据库）相比，Clerk 是商业托管服务：开箱即用、维护省心，但按活跃用户计费，且数据托管在 Clerk 侧。适合想快速上线、不愿自建用户系统的产品。

    Clerk 能开箱提供什么
    能力说明对应组件 / API
    登录方式邮箱密码、邮箱验证码、社交登录（Google/GitHub 等）<SignIn> / <SignUp>
    会话托管 Cookie、刷新令牌、多设备会话由 Clerk SDK 自动管理
    用户信息头像、姓名、邮箱、企业后台管理<UserButton> / currentUser()
    安全多因素认证、密码强度、防暴力破解后台开关配置
    数据同步用户注册/删除时回调你的后端Webhooks

    第一步：安装与环境变量

    终端
    npm install @clerk/nextjs

    在 Clerk 控制台创建应用后，把下面四个变量填进 .env.local（第 19 节讲过环境变量约定，不要加 NEXT_PUBLIC_ 前缀的这几个也是 Clerk 内部处理的）：

    .env.local
    NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_xxx
CLERK_SECRET_KEY=sk_test_xxx

    第二步：用 ClerkProvider 包裹根布局

    app/layout.tsx
    import { ClerkProvider } from "@clerk/nextjs";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <ClerkProvider>
      <html lang="zh-CN">
        <body>{children}</body>
      </html>
    </ClerkProvider>
  );
}

    第三步：中间件保护路由

    在项目根（或 src/ 下）加 middleware.ts。clerkMiddleware() 让 Clerk 在每个请求上注入登录态；用 createRouteMatcher 标出「公开路由」，其余未登录访问会被重定向到登录页。

    middleware.ts
    import { clerkMiddleware, createRouteMatcher } from "@clerk/nextjs/server";

// 标记公开路由：首页与登录注册页任何人可访问
const isPublicRoute = createRouteMatcher(["/", "/sign-in(.*)", "/sign-up(.*)"]);

export default clerkMiddleware((auth, req) => {
  if (!isPublicRoute(req)) {
    auth.protect(); // 未登录则重定向到登录页
  }
});

export const config = {
  // 排除静态资源，只对页面请求执行中间件
  matcher: ["/((?!_next|[^?]*\\.(?:html?|css|js(?!on)|jpg|png|svg)).*)"],
};

    第四步：页面里用声明式组件

    Clerk 提供一组开箱组件：<SignedIn> / <SignedOut> 按登录态切换内容，<SignInButton> / <SignUpButton> 触发弹窗式登录，<UserButton> 是右上角的用户头像下拉。

    app/page.tsx
    import { SignedIn, SignedOut, SignInButton, SignUpButton, UserButton } from "@clerk/nextjs";

export default function Home() {
  return (
    <header>
      <SignedOut>
        <SignInButton>登录</SignInButton>
        <SignUpButton>注册</SignUpButton>
      </SignedOut>
      <SignedIn>
        <UserButton />
      </SignedIn>
    </header>
  );
}

    服务端取用户与保护数据

    在服务端组件或路由处理程序里，用 auth() 拿当前用户的 ID，或用 currentUser() 拿完整用户对象。关键安全点：权限判断必须在服务端做，不要信任前端传来的身份。

    app/dashboard/page.tsx
    import { auth, currentUser } from "@clerk/nextjs/server";

export default async function Dashboard() {
  const { userId } = await auth(); // 未登录时为 null
  if (!userId) return null;          // middleware 之外的第二道防线

  const user = await currentUser();
  return <h1>欢迎，{user?.firstName}（id: {userId}）</h1>;
}
    常见坑：把 auth() 当客户端 Hook 用›

    auth() / currentUser() 来自 @clerk/nextjs/server，只能在服务端（服务端组件、Route Handler、Server Action、中间件）调用。在客户端组件里要改用 useUser() / useAuth() 这类 Hook。导入路径选错会直接报错。

    Webhook：把用户数据同步到自己的库

    Clerk 托管了用户账号，但你的业务库（如第 46 节 Prisma）里往往也要有一份用户记录。在 Clerk 控制台配置一个 Webhook，当用户注册、更新、删除时，Clerk 会向你的一个 Route Handler 发请求。

    app/api/webhooks/clerk/route.ts
    import { headers } from "next/headers";
import { Webhook } from "svix"; // Clerk 官方推荐的验签库

export async function POST(req: Request) {
  const payload = await req.json();
  const headerPayload = headers();
  const svix_id = headerPayload.get("svix-id") ?? "";
  const svix_timestamp = headerPayload.get("svix-timestamp") ?? "";
  const svix_signature = headerPayload.get("svix-signature") ?? "";

  // 用 Webhook Secret 验签，确保请求确实来自 Clerk
  const wh = new Webhook(process.env.CLERK_WEBHOOK_SIGNING_TOKEN!);
  const evt = wh.verify(JSON.stringify(payload), {
    "svix-id": svix_id,
    "svix-timestamp": svix_timestamp,
    "svix-signature": svix_signature,
  }) as { type: string };

  if (evt.type === "user.created") {
    // TODO: 在自己的数据库里创建对应用户记录
  }
  return new Response("ok", { status: 200 });
}

    定价与自托管提示

    • Clerk 是商业服务：按月活跃用户（Monthly Active Users，MAU）计费，个人 / 小项目通常在免费额度内，产品做大后要评估成本。
    • 数据在 Clerk 侧托管；若你的合规要求是「用户数据必须存在自己的服务器」，需要评估托管边界，或改选自托管方案（如 next-auth + 自建数据库）。
    • 从旧版 @clerk/nextjs（曾用 authMiddleware）迁移到 Core 2 时，中间件写法已统一为 clerkMiddleware()，以官方最新文档为准。
    最佳实践：中间件 + 服务端校验双保险›

    auth.protect() 挡住了「整页级」的访问，但具体到某条数据（如「只能看自己的笔记」），仍要在服务端取数时用 auth().userId 做行级过滤。永远不要假设「前端隐藏了按钮，用户就不会直接调接口」。
