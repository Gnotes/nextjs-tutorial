    概念与背景

    tRPC（TypeScript Remote Procedure Call）是一个用于 TypeScript 全栈应用的端到端类型安全的 API 层。它的核心主张是：前后端共享同一份 TypeScript 类型，不需要手写 OpenAPI / GraphQL Schema，也不需要代码生成步骤。后端把路由（router）定义好，前端通过导入这个 router 的类型，就能自动获得"能调哪些过程、传什么参、返回什么类型"的完整提示。

    传统做法下，后端写 /api/user/:id 返回 { id, name, email }，前端要靠文档或手写接口类型才能对上；一旦后端改了字段名，前端往往要到运行时才报错。tRPC 把这条链路变成编译期检查：后端删了一个字段，前端引用它的那一行立刻飘红。

    与 REST / GraphQL 的对比

    三种 API 风格的取舍
    方案类型安全学习/维护成本适用场景
    REST + fetch无（手写类型，易漂移）低公开接口、多语言客户端
    GraphQL需写 Schema + 代码生成高（服务端、缓存都要学）复杂查询、聚合多数据源
    tRPC原生端到端类型安全，零代码生成中（仅限 TS 全栈）TS 内部全栈、前后端同仓库
    tRPC 的代价：它要求前后端都是 TypeScript。一旦你需要一个非 TS 的客户端（如移动端原生、Python 服务），就该回到 REST/GraphQL。

    核心概念

    理解 tRPC 只需抓住五个词：

    • router（路由器）：一组过程（procedure）的命名容器，可以嵌套子路由。
    • procedure（过程）：一个可被远程调用的函数，分两类——query（读，幂等）与 mutation（写）。
    • input 校验：用 Zod（第 63 节）声明入参 schema，tRPC 在服务端自动校验，校验失败直接返回错误。
    • middleware（中间件）：在过程执行前后插入逻辑（如鉴权、打日志），可把数据注入 context。
    • context（上下文）：每次请求开始时构造的对象（如当前会话、数据库客户端），在所有过程里可访问。
    src/server/api/trpc.ts（tRPC 初始化与过程工厂）
    import { initTRPC, TRPCError } from "@trpc/server";
import { headers } from "next/headers";
import { db } from "~/server/db";

// 1) 每次请求构造 context：这里拿到请求头，后续可解析出当前会话
export async function createTRPCContext() {
  const heads = headers();
  return { db, headers: heads };
}
type TRPCContext = Awaited<typeof createTRPCContext>;

// 2) 初始化 tRPC，把 context 类型挂上去（整个后端只做一次）
const t = initTRPC.context<TRPCContext>().create();

export const createTRPCRouter = t.router;
export const publicProcedure = t.procedure; // 公开过程，无需登录

// 3) 鉴权中间件：把"必须登录"做成可复用的过程前缀
const enforceUserIsAuthed = t.middleware(({ ctx, next }) => {
  // 真实项目里从 ctx.headers 解析 session（见第 68 节）
  const userId = "user_123";
  if (!userId) throw new TRPCError({ code: "UNAUTHORIZED" });
  return next({ ctx: { ...ctx, userId } });
});

export const protectedProcedure = t.procedure.use(enforceUserIsAuthed);
    src/server/api/routers/user.ts（子路由）
    import { z } from "zod";
import { createTRPCRouter, publicProcedure, protectedProcedure } from "../trpc";

export const userRouter = createTRPCRouter({
  // query：读取。input 用 z.object 声明，服务端自动校验
  getById: publicProcedure
    .input(z.object({ id: z.string() }))
    .query(async ({ ctx, input }) => {
      const user = await ctx.db.user.findUnique({ where: { id: input.id } });
      return user; // 返回值类型自动被前端推导出
    }),

  // mutation：写入。必须登录才能改资料
  updateName: protectedProcedure
    .input(z.object({ name: z.string().min(1) }))
    .mutation(async ({ ctx, input }) => {
      return ctx.db.user.update({
        where: { id: ctx.userId },
        data: { name: input.name },
      });
    }),
});
    src/server/api/root.ts（合并成应用路由）
    import { createTRPCRouter } from "./trpc";
import { userRouter } from "./routers/user";

export const appRouter = createTRPCRouter({
  user: userRouter, // 前端调用形如 api.user.getById
});

// 导出路由类型：这是前后端"类型桥梁"的关键
export type AppRouter = typeof appRouter;

    在 Next.js App Router 中集成

    App Router 下，tRPC 通过一个捕获所有路由的 Route Handler 暴露出来；服务端组件（RSC）里可以直接用 createCaller 调用过程（不经网络），客户端组件则用 createTRPCReact 配 TanStack Query。

    src/app/api/trpc/[trpc]/route.ts（HTTP 入口）
    import { fetchRequestHandler } from "@trpc/server/adapters/fetch";
import { appRouter } from "~/server/api/root";
import { createTRPCContext } from "~/server/api/trpc";

const handler = (req: Request) =>
  fetchRequestHandler({
    endpoint: "/api/trpc",
    req,
    router: appRouter,
    createContext: createTRPCContext,
  });

export { handler as GET, handler as POST };
    src/trpc/react.tsx（客户端 Provider）
    "use client";
import { useState } from "react";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { httpBatchLink } from "@trpc/client";
import { createTRPCReact } from "@trpc/react-query";
import type { AppRouter } from "~/server/api/root";

export const trpc = createTRPCReact<AppRouter>();

export function TRPCProvider({ children }: { children: React.ReactNode }) {
  const [queryClient] = useState(() => new QueryClient());
  const [trpcClient] = useState(() =>
    trpc.createClient({ links: [httpBatchLink({ url: "/api/trpc" })] })
  );
  return (
    <trpc.Provider client={trpcClient} queryClient={queryClient}>
      <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>
    </trpc.Provider>
  );
}
    客户端页面调用（类型自动推导）
    "use client";
import { trpc } from "~/trpc/react";

export function UserProfile({ id }: { id: string }) {
  // 点 api. 时会自动补全 user.getById / user.updateName，参数与返回值全类型
  const { data, isLoading } = trpc.user.getById.useQuery({ id });
  const update = trpc.user.updateName.useMutation();

  if (isLoading) return <p>加载中…</p>;
  return (
    <button onClick={() => update.mutate({ name: "新名字" })}>
      {data?.name}
    </button>
  );
}

    类型推断：inferRouterOutputs

    当你需要在组件里手动标注"某个过程返回的数据类型"时，用 inferRouterOutputs / inferRouterInputs 从 AppRouter 反推类型，而不是手写重复的接口定义。

    src/types.ts
    import type { inferRouterOutputs, inferRouterInputs } from "@trpc/server";
import type { AppRouter } from "~/server/api/root";

// 后端返回的 User 类型：改后端这里自动跟着变
type UserOutput = inferRouterOutputs<AppRouter>["user"]["getById"];
// 前端传参类型
type UpdateNameInput = inferRouterInputs<AppRouter>["user"]["updateName"];

export type User = NonNullable<UserOutput>;

    常见坑›
    • query 与 mutation 用反：读取用 .query（前端 useQuery），写用 .mutation（前端 useMutation）。混用会导致缓存与重试行为不符合预期。
    • 忘了导出 type AppRouter：前端拿不到类型就退回到"无类型 API"，tRPC 的价值荡然无存。
    • 版本差异：tRPC 从 v10 到 v11，客户端从 @trpc/react-query 迁移到 @trpc/client + createTRPCReact，网上旧教程的 import 路径可能已变，以官方文档为准。
    最佳实践›
    1. 按业务域拆子路由：user、list、task 各一个文件，root.ts 只做合并，避免单文件膨胀。
    2. 把鉴权做成 protectedProcedure，敏感过程一律挂它，而不是在每个过程里手写 if。
    3. 入参一律用 Zod，不要裸传对象；这样前后端共享校验规则。
    4. 服务端组件里优先 createCaller 直调，省一次往返；只有需要交互/缓存时才走客户端 trpc.。
