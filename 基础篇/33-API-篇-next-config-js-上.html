API 篇 | next.config.js（上）

next.config.js 是 Next.js 唯一的运行期配置入口：它不是 JSON，而是一个会在服务端与构建阶段加载的 Node.js 模块。本节讲它的基本形态、类型校验，以及一批最常用的配置项：reactStrictMode、output、images、env、distDir 等。下半节讲 headers/rewrites 等路由函数。

    next.config.js 的基本形态

    Next.js 通过项目根目录（与 package.json 同级）下的 next.config.js 进行配置。它是一个普通的 Node.js 模块（不是 JSON），在服务端与构建阶段被加载，不会被打进浏览器产物。默认导出一个配置对象即可：

    next.config.js
    // @ts-check
/** @type {import('next').NextConfig} */
const nextConfig = {
  /* 配置项写在这里 */
}

module.exports = nextConfig

    几种等价写法：

    • ECMAScript 模块：用 next.config.mjs 写 export default nextConfig（remark/rehype 等 ESM-only 插件生态需要它）。
    • TypeScript：用 next.config.ts，直接 import type { NextConfig } from 'next' 标注类型。
    • 函数形式：可导出一个函数 (phase, { defaultConfig }) => nextConfig，根据 phase（当前加载阶段，从 next/constants 导入）区分开发/生产配置；Next 12.1.0 起还支持异步函数。
    注意›

    next.config 不支持 .cjs / .cts 扩展名。它不会被 webpack 或 Babel 转译，所以不要使用目标 Node 版本不支持的新语法。所有配置项都是可选的——不需要理解每一个，按需查阅即可。

    reactStrictMode

    开启 React 严格模式，帮你在开发期发现副作用、不安全生命周期等问题。Next.js 完整运行时已兼容严格模式，官方默认建议开启：

    next.config.js
    module.exports = {
  reactStrictMode: true,
}

    output：导出模式

    控制构建产物形态。'export' 静态导出（见第 32 节）；'standalone' 让输出只包含运行所需的最小文件集，配合 Docker 部署可大幅减小镜像体积（详见第 34 节）：

    next.config.js
    module.exports = {
  output: 'standalone', // 或 'export'
}

    images：图片配置

    配置 next/image 的加载器行为。最常用的是 remotePatterns（允许优化的远程图片源）、formats（输出现代格式）和 deviceSizes/imageSizes：

    next.config.js
    module.exports = {
  images: {
    // 允许 next/image 优化来自这些域名的远程图片
    remotePatterns: [
      {
        protocol: 'https',
        hostname: 'cdn.example.com',
        // pathname: '/assets/**', // 可进一步限定路径
      },
    ],
    // 优先输出现代图片格式
    formats: ['image/avif', 'image/webp'],
  },
}
    常见坑：漏掉 remotePatterns 导致 400›

    在 App Router 中，引用未在 images.remotePatterns 白名单里的远程图片，构建/请求时会报错。旧教程里写的 domains: [...] 已被 remotePatterns 取代（前者仍兼容但官方推荐后者，因为它能限定协议与路径）。

    env：构建期注入环境变量

    env 允许在构建时把变量内联进客户端包（注意：NEXT_PUBLIC_ 前缀的变量本来就会暴露到浏览器，这里是显式注入的手段）：

    next.config.js
    module.exports = {
  env: {
    CUSTOM_KEY: process.env.CUSTOM_KEY,
  },
}

    其余常用项一览

    next.config.js 常用配置（上）
    配置项作用 / 默认值
    poweredByHeader默认 true，会在响应头加 X-Powered-By: Next.js。生产建议关掉以隐藏技术栈。
    distDir构建输出目录，默认 .next。可改成自定义目录名。
    compress默认 true，对渲染内容与静态文件做 gzip 压缩（仅 server 模式生效）。
    generateEtags默认 true，为每个页面生成 ETag。按需关闭。
    httpAgentOptions默认对出站请求启用 HTTP Keep-Alive，可在此关闭。
    pageExtensions页面文件扩展名，默认 js/jsx/ts/tsx；接入 MDX 时加入 md/mdx（见第 30 节）。
    typedRoutes开启后 Link 的 href 有类型检查（详见第 34 节）。

    一个综合示例：

    next.config.js
    /** @type {import('next').NextConfig} */
const nextConfig = {
  reactStrictMode: true,
  poweredByHeader: false,
  compress: true,
  generateEtags: true,
  images: {
    remotePatterns: [{ protocol: 'https', hostname: 'cdn.example.com' }],
    formats: ['image/avif', 'image/webp'],
  },
}

module.exports = nextConfig

    experimental：实验性特性

    大量尚未稳定、需要 opt-in 的能力放在 experimental 命名空间下。官方会随版本增删，使用前务必核对当前版本文档。有代表性的几项：

    • mdxRs：用 Rust 写的 MDX 编译器（见第 30 节）。
    • optimizePackageImports：对图标库等做按需导入优化，减小包体积。
    • typedRoutes：也可在 experimental 下开启类型化路由。
    next.config.js
    module.exports = {
  experimental: {
    optimizePackageImports: ['lucide-react'],
  },
}
    常见坑：experimental 会随版本变动›

    experimental 里的字段可能在某个版本转正（移出 experimental）、改名或被移除。升级 Next 版本后如果构建报「未知配置项」，优先检查 experimental 里的字段是否已变更。

    最佳实践›
    1. 用 JSDoc /** @type {import('next').NextConfig} */ 或 next.config.ts 获得类型提示与拼写检查，避免手写出错。
    2. 生产环境默认关掉 poweredByHeader，减少技术栈暴露。
    3. 不要把敏感密钥写进 env——它会被打进客户端包，暴露给浏览器。
