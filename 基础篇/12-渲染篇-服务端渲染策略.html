渲染篇 | 服务端渲染策略

App Router 默认「能静态就静态，遇到动态能力自动切换」。本节讲清静态/动态渲染的切换条件、路由段配置项，以及如何读懂构建输出里的符号。

篇章：基础篇主题：渲染 · 策略篇幅：约 14 分钟

本节目录

    默认策略：能静态就静态

    第 08 节我们定义过静态站点生成（Static Site Generation，SSG）与服务端渲染（Server-Side Rendering，SSR）。在 App Router 里，Next.js 把它们统一成了两种默认渲染模式：

    • 静态渲染（Static Rendering）：路由在构建时（或被增量静态再生成，Incremental Static Regeneration，ISR，更新时）渲染一次，产物可缓存、可部署到内容分发网络（Content Delivery Network，CDN），多个用户共用。
    • 动态渲染（Dynamic Rendering）：路由在每次请求时于服务端渲染，可以读取实时的、与请求相关的信息（登录态、请求头、查询参数）。

    关键心智模型：默认走静态渲染；只要路由里用到了「只在请求时才知道」的能力，Next.js 就自动把该路由段切换为动态渲染。这是一种「 opt-out（退出式）」语义——你不主动做任何动态的事，它就尽量静态。

    路由段渲染
    →
    是否读取
    动态函数？
    →
    否：静态渲染
    (构建时/ISR)
    /
    是：动态渲染
    (每次请求)

    哪些行为会触发动态渲染

    下列「动态函数 / 动态 API」一旦在某路由段被调用，该路由段（以及其子树）就退出静态、进入动态渲染：

    • 读取请求级信息：cookies()、headers()。
    • 访问当前查询参数：searchParams（传给 page.tsx 的 prop）。
    • 声明为「不缓存」的数据请求：fetch(url, { cache: "no-store" })（或等价写法 next: { revalidate: 0 }）。
    • 路由段配置里强制动态（见下节）。
    app/page.tsx —— 读取 cookies 会把整段路由变为动态渲染
    import { cookies } from "next/headers"

export default async function AccountPage() {
  // 只要读了 cookie，这个页面就无法在构建时静态化，
  // 只能在每次请求时动态渲染
  const token = (await cookies()).get("session")?.value

  return <main>登录态：{token ? "已登录" : "未登录"}</main>
}

    路由段配置：手动控制策略

    除了被动地「被动态函数切换」，你也可以在 layout.tsx / page.tsx / route.ts 里导出路由段配置（Route Segment Config）常量，显式覆盖默认行为：

    app/admin/page.tsx —— 强制动态渲染
    // 强制每次请求都动态渲染（等价于禁用该段所有 fetch 缓存并始终重新取数）
export const dynamic = "force-dynamic"

export default async function AdminPage() {
  // 这里一定是请求时实时执行
  return <main>后台管理</main>
}
    app/about/page.tsx —— 强制静态渲染
    // 强制静态：即使里面不小心调用了动态 API，也要求它是静态的
export const dynamic = "force-static"

export default function AboutPage() {
  return <main>关于我们（几乎不变化）</main>
}

    dynamic 的取值：

    路由段 dynamic 配置取值
    取值含义
    "auto"（默认）尽量静态，组件用到动态能力时自动切到动态
    "force-dynamic"强制动态渲染，每次请求实时取数（与 SSR 等价）
    "force-static"强制静态渲染，构建/ISR 时产出，忽略动态读取
    "error"强制静态，若真用了动态 API 则直接构建报错，防止意外动态化

    revalidate：静态渲染与 ISR 的桥梁

    静态渲染不等于「一次构建、永不变更」。通过 revalidate，你可以让静态页面按周期在后台重新生成——这正是 ISR：

    app/blog/page.tsx —— 静态 + 每小时再验证
    // 这个路由段静态渲染，内容每 3600 秒后台重新验证一次（ISR）
export const revalidate = 3600

export default async function BlogPage() {
  const posts = await fetch("https://api.example.com/posts", {
    next: { revalidate: 3600 },
  }).then((r) => r.json())

  return <main>{posts.length} 篇文章</main>
}

    于是策略之间的关系变成：静态渲染是默认底座；force-dynamic 把它拉到「每次请求都现渲」的动态渲染；revalidate 则在静态底座上叠加「后台定时更新」的 ISR 能力。动态渲染与 ISR 是两个极端之间的连续谱。

    读懂构建输出里的符号

    跑 next build 时，终端会列出每条路由的渲染类型。常用符号：

    构建输出路由符号含义
    符号名称含义
    ○Static（静态）该路由构建时预渲染为静态内容，可缓存、可上 CDN
    ƒDynamic（动态）该路由在每次请求时于服务端按需渲染
    ●ISR / 带再验证的静态静态产出，但按 revalidate 周期后台更新

    示例输出（节选）：○ /about、ƒ /dashboard/[user]、● /blog/[slug]。上线后也可以用 curl -I 看响应头里的缓存标记（如 x-nextjs-cache）辅助判断命中了哪种策略。

    策略选择速查

    按页面特征选策略
    页面特征推荐策略做法
    几乎不变（官网、文档、关于页）静态渲染默认即可，不读动态 API
    内容会变，但不要求秒级新鲜静态 + ISR加 revalidate
    依赖登录态 / 个性化 / 实时数据动态渲染读 cookies()/headers() 或 force-dynamic
    明确要阻止意外动态化锁静态dynamic = "error" 兜底
    常见坑：以为加了 revalidate 就一定按时更新›

    和第 08 节强调过的一样：revalidate 是「过期后下一次访问触发后台重建」的惰性机制，不是定时器。页面只有在有人访问时才可能被刷新；对时效要求苛刻（秒杀、实时价格）的页面，应走动态渲染而非 ISR。

    提示：动态是「按路由段」传染的›

    一旦某层 layout/page 调用了动态 API，它和它的子路由段都按动态处理。这意味着一个深层页面里的 cookies() 调用，会让该分支整段退出静态化。做性能审计时，先看 build 输出里哪些路径标了 ƒ，再回头找它调用了哪个动态 API。

    最佳实践›
    • 能静态就静态：把取数尽量放在不依赖请求态的服务端组件里，默认享受静态/ISR 红利。
    • 把动态读取（cookies/headers）收窄到真正需要它的最小路由段，避免整棵子树被拖成动态。
    • 用 next build 的输出符号做回归检查：改动后确认关键页面仍是 ○ / ● 而不是意外变成 ƒ。
    • 需要强制语义时显式写 dynamic 配置，而不是靠「隐式副作用」决定策略。
