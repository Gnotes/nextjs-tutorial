    页面入参：params 与 searchParams

    在 App Router 里，page.tsx / layout.tsx 组件通过 props 接收路由信息。Next.js 15 起，这两个 props 都是 Promise，必须 await（v14 及更早是同步对象）。

    • params：动态路由段参数。如 app/blog/[slug]/page.tsx 对应 { slug: string }。
    • searchParams：URL 查询串，是一个普通对象（?q=next → { q: 'next' }）。
    app/blog/[slug]/page.tsx
    type Props = {
  params: Promise<{ slug: string }>
  searchParams: Promise<{ draft?: string }>
}

export default async function BlogPost({ params, searchParams }: Props) {
  const { slug } = await params
  const { draft } = await searchParams
  // ...
}
    常见坑：params 类型要写成 Promise›

    从 v15 起若仍按 v14 直接 params.slug 取值，TypeScript 会报错。类型注解必须写成 Promise<{...}> 再 await。这是 App Router 迁移到 v15 时改动面最大的一处之一。

    generateMetadata：动态生成元数据

    当元数据（标题、描述）依赖数据时，导出 generateMetadata 函数，它接收和页面相同的 props（含 v15 的 Promise 化 params/searchParams），返回一个 Metadata 对象：

    app/blog/[slug]/page.tsx
    import type { Metadata } from 'next'

export async function generateMetadata(
  { params }: { params: Promise<{ slug: string }> }
): Promise<Metadata> {
  const { slug } = await params
  const post = await getPost(slug)
  return {
    title: post.title,
    description: post.excerpt,
  }
}

    类似地，generateViewport 专门用于输出视口相关元数据（viewport、themeColor），从 metadata 中拆分出来独立导出，避免和基础 metadata 混杂。

    generateStaticParams：构建期枚举动态路由

    静态导出或静态渲染动态路由时，需要在构建期知道要预生成哪些路径。generateStaticParams 返回参数对象数组：

    app/blog/[slug]/page.tsx
    // 构建期预生成 welcome 与 about 两篇
export function generateStaticParams() {
  return [{ slug: 'welcome' }, { slug: 'about' }]
}

// 也可从数据源动态拉取全部文章 slug
// export async function generateStaticParams() {
//   const posts = await getAllPosts()
//   return posts.map((p) => ({ slug: p.slug }))

    配合 export const dynamicParams = false，未在列表中的 slug 会直接 404（见第 30 节博客 MDX 示例）。

    revalidatePath 与 revalidateTag：按需重新验证

    这两个是手动让缓存失效的手段，通常在 Server Action 或后台任务里调用：

    重新验证函数对比
    函数作用
    revalidatePath(path)按路由路径失效该路由的缓存（可传 '/blog' 或具体路径）。
    revalidateTag(tag)按标签失效——给 fetch 打 next: { tags: [...] } 标签，再按标签批量失效。
    app/actions.ts
    'use server'
import { revalidatePath } from 'next/cache'

export async function createPost() {
  // ...写库...
  revalidatePath('/blog')        // 让博客列表页缓存失效
}

    unstable_noStore（按需了解）

    从 next/cache 导出的 unstable_noStore() 用于在服务端组件内声明「本路由不做静态缓存，走动态渲染」。它是过渡 API，命名带 unstable。现代写法更推荐用路由段配置 export const dynamic = 'force-dynamic' 来达到同样目的（以官方文档当前状态为准）。

    NextRequest 与 NextResponse：路由处理器增强

    路由处理程序（Route Handler）的入参/返回值，在 Web 标准 Request/Response 之上做了封装，从 next/server 导入。NextRequest 在标准请求之上额外提供 .nextUrl（含已解析的查询参数、路径）、.cookies、.ip 等；NextResponse 提供 .redirect()、.rewrite()、.json() 等便捷静态方法。

    app/api/hello/route.ts
    import { NextRequest, NextResponse } from 'next/server'

export async function GET(request: NextRequest) {
  // 直接读查询参数，无需自行 new URL
  const search = request.nextUrl.searchParams.get('q')

  // 读 cookie
  const theme = request.cookies.get('theme')

  // 便捷返回 JSON
  return NextResponse.json({ q: search, theme: theme?.value })
}

    常见响应方法：

    NextResponse 常用静态方法
    方法作用
    NextResponse.json(data)返回 JSON 响应。
    NextResponse.redirect(url)返回重定向响应。
    NextResponse.rewrite(url)服务端重写（对外 URL 不变）。
    最佳实践›
    1. 新代码一律按 v15 Promise 化写法写 params/searchParams/cookies/headers，避免升级返工。
    2. 数据变化后用 revalidatePath（按页面）或 revalidateTag（按数据标签）精确失效，而非整站重建。
    3. 路由处理器里优先用 NextRequest.nextUrl 解析查询参数，省去手写 new URL(request.url)。
