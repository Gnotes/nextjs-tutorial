    三大路由函数：headers / redirects / rewrites

    这三个都是 async 函数，在 next.config.js 里导出，运行在服务端。它们的共同点是：返回一个数组，每项用 source 匹配请求路径。三者语义不同，务必分清：

    headers / redirects / rewrites 对比
    函数作用对浏览器地址栏的影响
    headers()给匹配的响应附加自定义 HTTP 头（安全头、缓存策略等）。不跳转，只是加头。
    redirects()把请求重定向到新地址（返回 3xx）。地址栏 URL 会变。
    rewrites()URL 重写（反向代理），对外 URL 不变，内部映射到别的目标。地址栏 URL 不变。

    每项配置的字段：source（匹配路径，支持参数与正则）、destination（rewrite/redirect 的目标）、permanent（redirect 是否 308 永久，否则 307 临时）、headers（headers 函数里的键值对）。

    headers() 示例

    next.config.js
    /** @type {import('next').NextConfig} */
const nextConfig = {
  async headers() {
    return [
      {
        // 对所有路由生效
        source: '/:path*',
        headers: [
          { key: 'X-Frame-Options', value: 'DENY' },
          { key: 'X-Content-Type-Options', value: 'nosniff' },
        ],
      },
      {
        // 只给 /api 下的响应加缓存头
        source: '/api/:path*',
        headers: [
          { key: 'Cache-Control', value: 'public, max-age=3600' },
        ],
      },
    ]
  },
}
module.exports = nextConfig

    redirects() 示例

    next.config.js
    async redirects() {
  return [
    // /old-post → /blog/post，308 永久重定向（利于 SEO）
    { source: '/old-post', destination: '/blog/post', permanent: true },
    // 带动态参数：/docs/v1/foo → /docs/v2/foo
    { source: '/docs/v1/:slug*', destination: '/docs/v2/:slug*', permanent: false },
  ]
}

    rewrites()：beforeFiles 与 afterFiles

    rewrites 可以返回一个对象，分三段控制匹配顺序，这是它最容易踩坑的地方：

    • beforeFiles：最先匹配，在 Next 自己的页面/文件系统路由之前。常用于反代外部服务。
    • afterFiles：在 Next 页面路由之后匹配——即先尝试命中真实页面，没命中才走重写。常用于给不存在的路径做兜底。
    • fallback：连动态路由都没命中后再匹配，SPA 兜底。
    next.config.js
    async rewrites() {
  return {
    // 先于 Next 页面：/proxy/xxx 反代到外部 API
    beforeFiles: [
      { source: '/proxy/:path*', destination: 'https://api.example.com/:path*' },
    ],
    // 页面没命中时再尝试：/about 兜底到外部
    afterFiles: [
      { source: '/about', destination: 'https://other.example.com/about' },
    ],
  }
}
    常见坑：rewrites 与静态导出不兼容›

    rewrites / redirects / headers 都是服务端运行期行为，与第 32 节的 output: 'export' 静态导出互不兼容——它们需要服务器执行。纯静态托管请改用 Nginx/CDN 层做等价的重写与跳转。

    basePath 与 trailingSlash

    basePath 把整个应用挂到域名子路径下（常见于同域多应用、GitHub Pages 项目站点）；trailingSlash 控制路由末尾斜杠的处理：

    next.config.js
    module.exports = {
  // 应用部署在 https://example.com/docs 下
  basePath: '/docs',
  // /me 自动带成 /me/，静态导出时生成 /me/index.html
  trailingSlash: true,
}

    设了 basePath: '/docs' 后，代码里写 <Link href="/about"> 会自动变成 /docs/about，无需手动拼接。

    webpack 自定义

    极少数情况下需要接管 webpack 配置（如加别名、加载特殊文件）。通过 webpack(config, { isServer }) 函数返回修改后的 config：

    next.config.js
    module.exports = {
  webpack(config, { isServer }) {
    // 示例：加一个 @ → src 别名（实际更推荐 tsconfig paths）
    config.resolve.alias['@'] = require('path').join(__dirname, 'src')
    return config
  },
}
    常见坑：谨慎修改 webpack›

    直接改 webpack 容易破坏 Next 内置的打包行为。能用 tsconfig.json 的 paths 解决的别名问题就别碰 webpack；且项目切换到 Turbopack 后部分 webpack 配置不再生效，应优先考虑官方配置项。

    outputFileTracing 与 standalone

    Next.js 会自动追踪每个页面运行时真正依赖的文件，用于精简部署产物。配合 output: 'standalone' 会在 .next/standalone 输出一份只含运行所需文件的目录（连 node_modules 都精简），这是 Docker 部署减小镜像体积的关键：

    next.config.js
    module.exports = {
  output: 'standalone',
  // 默认 true；如需关闭文件追踪可设为 false
  outputFileTracing: true,
}

    eslint 与 typedRoutes

    eslint 配置控制生产构建时对 ESLint 错误的处理策略；typedRoutes 开启后，next/link 的 href、router.push 等都会被 TypeScript 校验是否为真实存在的路由：

    next.config.js
    module.exports = {
  eslint: {
    // 生产构建时忽略 ESLint 错误（CI 里仍可单独跑 lint）
    ignoreDuringBuilds: false,
  },
  experimental: {
    typedRoutes: true,
  },
}

    开启 typedRoutes 后，写错路由（如 href="/usrs"）会在编辑器里立刻报红，是大型项目里很值得开的一项。

    最佳实践›
    1. 把安全响应头（X-Frame-Options、Referrer-Policy 等）集中写在 headers() 里，而不是散落在各路由。
    2. 做服务端部署（Docker）时默认 output: 'standalone'，镜像体积可大幅缩小。
    3. 大型项目尽早开 typedRoutes，路由改名时能在编译期发现所有引用处。
