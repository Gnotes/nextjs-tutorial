渲染篇 | Suspense 与 Streaming

不要再等整页数据准备好才吐 HTML：用 Suspense 做边界、用 loading.tsx 出骨架屏，让服务端把页面「边渲染边发」给浏览器。

篇章：基础篇主题：渲染 · Streaming篇幅：约 13 分钟

本节目录

    为什么需要 Streaming

    传统服务端渲染（SSR）有个通病：服务器必须把整棵组件树、连同它依赖的所有数据全部准备好，才能拼出第一段 HTML 返回给浏览器。这期间浏览器一直白屏——最慢的那一块数据，拖累了整个首屏。

    流式传输（Streaming）换了一种吐字方式：服务端不用等整页就绪，而是先把「已经想好的部分」（比如布局、导航、静态外壳）先发给浏览器，浏览器立刻开始渲染、可以先看到页面框架；剩下还在等数据的区块，用一个占位（骨架屏）顶上，等数据好了再「补」上去。

    阻塞式 SSR：等所有数据就绪
    →
    一次性返回整页 HTML
    先发页面骨架
    + 已就绪区块
    →
    慢区块先显示骨架屏
    →
    数据就绪后
    逐段补发并替换
    →
    页面分段可用

    好处是直观的：首字节时间（Time To First Byte，TTFB）下降，用户先看到有内容的页面；慢数据不会阻塞快内容的展示。

    React Suspense：流式的「边界」原语

    流式不是随便切分页面，它由 React 的 Suspense 组件划定边界。用法是用 <Suspense fallback={...}> 把一块可能异步的区域包起来：当里面的组件还在等数据时，先显示 fallback 指定的占位 UI；等数据就绪，React 自动用真实内容替换它。

    app/page.tsx — 用 Suspense 包裹慢组件
    import { Suspense } from "react"
import { SlowProfile, FastNav, Skeleton } from "@/ui"

export default function Page() {
  return (
    <main>
      <FastNav />
      {/* 这块依赖慢查询：没好之前先显示骨架屏 */}
      <Suspense fallback={<Skeleton />}>
        <SlowProfile />
      </Suspense>
    </main>
  )
}

    这里 SlowProfile 是一个内部 await 了慢查询的服务端组件。Suspense 边界告诉 React：「这块独立流式，别让它拖住别人」。

    loading.tsx：零代码的页面级 Suspense 边界

    在 App Router 里，你甚至可以不手写 <Suspense>。只要在某个路由段目录里加一个 loading.tsx，Next.js 会自动把该路由段的 page.tsx（及其下方所有子路由）包进一个 Suspense 边界，并用 loading.tsx 作为 fallback。

    app/dashboard/loading.tsx — 骨架屏
    // 路由段目录里放一个 loading.tsx，Next.js 自动包裹 Suspense
export default function Loading() {
  return (
    <div className="animate-pulse p-6">
      <div className="h-6 w-1/3 rounded bg-slate-700" />
      <div className="mt-4 h-24 rounded bg-slate-800" />
      <div className="mt-2 h-24 rounded bg-slate-800" />
    </div>
  )
}

    目录结构与行为如下：loading.tsx 嵌套在同级 layout.tsx 之内，layout 先稳定渲染，page 的内容再流式补进来。

    layout.tsx（先渲染并保持稳定）
    ↓
    loading.tsx（骨架屏立即展示）
    ↓
    page.tsx 数据就绪，自动替换骨架屏

    嵌套路由示例：不同层级各自流式

    因为 loading.tsx 是按路由段生效的，你可以在不同层级放不同的骨架屏，实现「页面外壳先出、局部区块再填」的渐进式加载：

    app/(shop)/ —— 目录结构
    app/(shop)/
├── layout.tsx          // 商品区整体布局（稳定先渲染）
├── loading.tsx         // 商品区级骨架屏
├── page.tsx            // 商品列表
└── products/
    ├── layout.tsx
    ├── loading.tsx     // 单个商品详情级骨架屏
    └── [slug]/page.tsx

    用户访问 /products/abc 时：外层布局立刻可见 → products/loading.tsx 的骨架屏顶上 → [slug]/page.tsx 把商品详情查回来后，再替换掉骨架屏。

    error.tsx：流式失败时的边界

    有成功的流式，就要考虑失败的流式。如果某个路由段在流式渲染时抛错，不能让整页白屏。和 loading.tsx 对称，放一个 error.tsx 就能捕获该路由段渲染期的错误并显示兜底界面，而不影响布局等已经流式输出的部分。

    app/dashboard/error.tsx — 错误兜底
    "use client" // error.tsx 必须是客户端组件
export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string }
  reset: () => void
}) {
  return (
    <div>
      <h2>出了点问题</h2>
      <button onClick={() => reset()}>重试</button>
    </div>
  )
}

    注意 error.tsx 必须是客户端组件（要捕获错误、提供重试交互），这是它和纯服务端 loading.tsx 的一个区别。

    Streaming 与 SEO

    一个常见疑问：流式输出会不会影响搜索引擎优化（Search Engine Optimization，SEO）？答案是不影响——和传统 SSR 一样，搜索引擎爬虫可以等到流式内容全部到达后再索引，最终服务端仍然把完整 HTML 发出去；浏览器只是「边收边渲」，并不是把内容留在客户端才渲染。真正对 SEO 不友好的是 CSR（空壳 HTML），流式 SSR 与它本质不同。

    常见坑：整页 loading.tsx 等于把流式退化成阻塞式›

    如果你只在根 app/ 放一个覆盖整页的 loading.tsx，确实能出骨架屏，但慢数据仍会拖住整个首屏——因为你把边界放到了最外层。想要分段流式，就要在较慢的区块粒度上用 <Suspense>，或在更深的路由段放 loading.tsx。

    提示：布局不随导航重渲染›

    流式配合路由布局有个额外福利：layout.tsx 在导航间保持不变，不会因为子路由流式加载而重新渲染。这也是为什么先渲染布局、再流式补 page 体感很顺滑。

    最佳实践›
    • 为每个数据驱动的路由段都提供 loading.tsx 骨架屏，首屏立刻有反馈。
    • 把慢数据组件单独用 <Suspense> 包起来，别让一个慢查询阻塞整页。
    • 同步配 error.tsx 兜底，避免流式中途报错导致白屏。
    • 骨架屏尺寸尽量接近真实内容布局，减少加载完成后的视觉跳动（CLS）。
