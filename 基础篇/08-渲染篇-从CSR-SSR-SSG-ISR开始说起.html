渲染篇 | 从 CSR、SSR、SSG、ISR 开始说起

本节梳理 Web 渲染演进出的四种主流方式：客户端渲染（Client-Side Rendering，CSR）、服务端渲染（Server-Side Rendering，SSR）、静态站点生成（Static Site Generation，SSG）与增量静态再生成（Incremental Static Regeneration，ISR），讲清各自的概念、流程、优缺点与选型依据。这是理解 Next.js 一切渲染行为的地基。

    概念与背景

    Web 渲染方式不是凭空发明的，而是跟着时代问题一步步演化出来的：早期的网站是服务端拼好 HTML 直接下发；前端框架兴起后流行"页面由 JavaScript 在浏览器里渲染"；随后人们发现这种模式在首屏速度与搜索引擎收录上存在短板，于是服务端渲染与静态化方案回归，最后又演化出兼顾两者的增量方案。一句话总结：这四种方式的本质区别是"HTML 在哪里、什么时候被生成"。

    • CSR：HTML 在浏览器里生成（客户端）。
    • SSR：HTML 在服务器上、每次请求时实时生成。
    • SSG：HTML 在构建时生成，之后不再变化。
    • ISR：HTML 在构建时生成，但可以在运行期按策略后台更新。

    Next.js 的价值就在于：它让你在同一个框架、同一套组件代码里，按页面粒度自由选择上述任何一种策略，而不必为每种方案搭建不同的工程体系。接下来逐个展开。

    客户端渲染（Client-Side Rendering，CSR）

    概念与流程

    CSR 是 React、Vue 等传统单页应用（Single Page Application，SPA）的默认形态：服务器只返回一个几乎空的 HTML 外壳和一堆脚本链接，浏览器下载并执行 JavaScript，再由 JavaScript 请求数据、渲染出完整页面。

    请求页面
    →
    返回空壳 HTML
    + 脚本引用
    →
    下载并执行 JS
    →
    JS 请求数据
    →
    浏览器渲染完整页面

    优点

    • 服务器只出静态资源，压力小、成本低，可以整体挂到内容分发网络（Content Delivery Network，CDN）。
    • 页面切换无需整页刷新，交互体验流畅（SPA 特性）。
    • 开发模型简单：纯前端工程，不依赖 Node 服务。

    缺点

    • 首屏白屏时间长：要等 JS 下载、执行完才看得到内容，首屏渲染慢。
    • 对搜索引擎（Search Engine Optimization，SEO）不友好：爬虫拿到的是空壳，内容在 JS 执行后才出现，部分爬虫无法等到这一步。
    • Bundle 体积越大，白屏越久，需要额外做代码分割。

    服务端渲染（Server-Side Rendering，SSR）

    概念与流程

    SSR 指在服务器上执行 React 渲染，把组件直接渲染成完整的 HTML 字符串返回给浏览器；浏览器拿到的是有内容的页面，之后再进行水合（Hydration）——把事件监听和交互状态"附"到已渲染的 DOM 上。

    请求页面
    →
    服务端执行 React
    渲染出 HTML
    →
    返回完整 HTML
    →
    客户端水合
    (Hydration)
    →
    可交互页面

    优点

    • 首屏内容完整、可被搜索引擎抓取，SEO 友好。
    • 每次请求实时生成，适合个性化内容、实时数据（如登录态、价格、库存）。
    • 数据请求发生在服务端，响应更快且不会向浏览器暴露内部逻辑。

    缺点

    • 每个请求都要在服务器上执行一次渲染，并发高时服务器压力大、成本高。
    • 水合仍需要下载 JS，交互就绪时间未必比 CSR 快太多。

    静态站点生成（Static Site Generation，SSG）

    概念与流程

    SSG 指在构建（Build）阶段就把页面预渲染成纯静态 HTML 文件，部署到 CDN 后，任何请求都直接命中静态文件，连服务器都不用跑。

    构建时(Build)
    预渲染
    →
    生成静态 HTML 文件
    →
    部署到 CDN
    →
    请求直接返回静态文件

    优点

    • 性能最好：CDN 边缘节点直接吐文件，首屏极快。
    • 成本最低：不需要渲染服务器，天然抗突发流量。
    • SEO 友好：内容是构建时就确定好的完整 HTML。

    缺点

    • 内容更新需要重新构建并重新部署，时效性差。
    • 不适合依赖用户登录态、个性化数据的页面（除非配合客户端再获取数据）。

    增量静态再生成（Incremental Static Regeneration，ISR）

    概念与流程

    ISR 由 Vercel 团队提出，目标是"既想有 SSG 的性能，又想要内容保鲜"。思路是：页面仍然静态生成，但可以配置一个重新验证（Revalidation）周期，或通过按需（On-Demand）方式触发，在后台重新生成页面并替换旧版本；在重新生成完成之前，旧页面继续对外服务。

    请求页面
    →
    命中已有静态页
    (可能已过期)
    →
    先返回旧页面
    后台触发重新生成
    →
    重新生成完成
    更新缓存
    →
    后续请求拿到新页面

    优点

    • 保留 SSG 的性能与成本优势，同时让内容能定期或在数据变更时更新。
    • 无需全站重新构建，只需重新生成受影响页面（增量）。

    缺点

    • 存在"过期窗口"：用户可能短暂看到旧内容。
    • revalidate 是"下次访问时检查是否过期"的惰性机制，不是精确的定时任务，触发时机需要理解清楚。

    四种方式对比总表

    CSR / SSR / SSG / ISR 横向对比
    维度CSRSSRSSGISR
    HTML 生成时机浏览器端每次请求时（服务端）构建时构建时 + 按需后台更新
    首屏速度慢（白屏）中（需服务端渲染）最快（CDN 直出）最快（CDN 直出）
    SEO差好好好
    内容新鲜度实时实时构建时定格周期/按需更新
    服务端依赖无（纯静态资源）高（每个请求渲染）无（纯静态）需要生成服务（如 Vercel）
    典型场景后台管理、工具类应用个性化、实时数据页面官网、博客、文档内容经常更新的博客/电商列表

    在 Next.js 中的最小示例

    在 App Router 里，同一个页面组件可以通过路由段配置在四种策略间切换。下面是两种最常见的形态：ISR 与强制动态渲染（服务端渲染）：

    app/posts/[slug]/page.tsx
    // 形态一：ISR —— 构建时预渲染，之后每 3600 秒在后台重新生成一次
export const revalidate = 3600;

export default async function Page({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const post = await getPost(slug);
  return <article>{post.title}</article>;
}
    app/dashboard/page.tsx
    // 形态二：强制动态渲染（SSR 行为）——每次请求都在服务端重新渲染
export const dynamic = 'force-dynamic';

export default async function Dashboard() {
  const user = await getCurrentUser(); // 依赖登录态，必须实时
  return <main>你好，{user.name}</main>;
}

    其余两种形态对应的配置写法：客户端数据获取（CSR 行为）由客户端组件配合 fetch 或 SWR 完成；纯静态（SSG 行为）则是默认形态——只要页面不依赖动态函数，构建时就会被静态预渲染。第 12 节「服务端渲染策略」会完整讲解这些配置的边界。

    如何选择

    一个实用的决策顺序：

    1. 页面内容是否依赖"当前请求者"（登录态、个性化）？是 → 走 CSR 或 SSR。
    2. 内容变化是否频繁？几乎不变 → SSG；隔一段时间变一次 → ISR；随时在变 → SSR（或 CSR + 客户端数据请求）。
    3. 对首屏与 SEO 的要求高不高？官网、博客、营销页 → 优先 SSG / ISR；后台系统 → CSR 足够。

    在 Next.js 的 App Router 中，默认行为是"能静态就静态，用到动态能力就自动切到服务端渲染"，具体策略边界在第 12 节「服务端渲染策略」中展开。

    常见坑：ISR 的 revalidate 语义›

    revalidate 不是"每 N 秒自动刷新一次"的定时器，而是"页面在上次生成后超过 N 秒，下一次访问时触发后台重新生成"。也就是说，页面只在有人访问时才可能被刷新；无人访问的页面不会自动更新。需要精确时效的场景（如倒计时、秒杀）不适合 ISR。

    提示：把四种方式理解为"HTML 在哪生成"›

    面试和开发中都建议用这句话建立直觉：CSR 在浏览器生成、SSR 在服务器实时生成、SSG 在构建时生成、ISR 在构建时生成但允许运行期增量更新。后续 9-12 节会把它落到 Next.js 的具体 API 上。

    最佳实践：从官方示例动手验证›
    1. 用 npx create-next-app@latest 建一个默认 App Router 项目，分别体验：客户端数据请求（CSR 行为）、fetch 加 revalidate（ISR 行为）、generateStaticParams（SSG 行为）。
    2. 参考官方示例仓库 vercel/next.js 下的 with-static-export、reproduction-* 相关示例理解边界行为。
    3. 用 curl -i 查看响应头中的缓存标记（如 x-nextjs-cache），观察不同策略下响应缓存状态的变化。
