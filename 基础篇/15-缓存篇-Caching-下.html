    概念与背景

    上一节建立了四层缓存的全景；这一节解决工程问题：每一层怎么配、怎么主动让它失效、怎么观察它到底有没有命中。很多「数据改了页面不更新」「页面意外变成动态渲染」的问题，本质都是对这几个开关的作用范围理解不清。

    先记住一张总图：配置手段分三个粒度——单个 fetch、单个路由段、整个应用；失效手段分两类——时间驱动（自动）与事件驱动（手动）。

    单请求粒度
    fetch(url, opts)
    →
    路由段粒度
    page/layout/route 导出

    应用粒度
    next.config.js

    配置：三个粒度

    粒度一：单个 fetch

    app/lib/data.ts
    // 完全不缓存，每次实时拉取
fetch(url, { cache: 'no-store' })

// 显式进数据缓存（Next.js 15+ opt-in）
fetch(url, { cache: 'force-cache' })

// 进缓存 + 3600 秒后重新验证 + 打标签
fetch(url, {
  next: { revalidate: 3600, tags: ['posts'] },
})

    粒度二：路由段配置（Route Segment Config）

    在 page.tsx / layout.tsx / route.ts 里 export 常量，影响整个路由段：

    常用路由段配置项
    导出项作用
    export const dynamic = 'force-dynamic'强制动态渲染，等价于段内所有 fetch 都 no-store
    export const dynamic = 'force-static'强制静态渲染，cookies/headers 等返回空值
    export const revalidate = 60该段默认重新验证周期（秒）；0 = 始终动态；false = 永久缓存
    export const fetchCache = 'force-no-store'段内所有 fetch 一律不缓存（高级选项，谨慎用）
    app/blog/[slug]/page.tsx
    // 这个路由段默认每 60 秒重新验证一次
export const revalidate = 60

// 强制走动态渲染：每次请求都实时取数
export const dynamic = 'force-dynamic'

    粒度三：整个应用

    next.config.ts
    const nextConfig = {
  experimental: {
    // 调整客户端路由缓存（Router Cache）的自动过期时间
    staleTimes: {
      dynamic: 30, // 动态段秒数
      static: 180, // 静态段秒数
    },
  },
}
export default nextConfig

    失效：两条路径

    时间驱动：到点自动重新验证

    如第 13 节所述，next: { revalidate: N } 让数据在 N 秒后「过期」，下次访问先返回旧数据、后台刷新。注意规则：同一路由所有布局/页面里 revalidate 的最小值，决定整条路由的重新验证频率——子路由不能比父布局更久。

    事件驱动：按需重新验证（On-Demand Revalidation）

    app/actions.ts
    'use server'
import { revalidatePath, revalidateTag } from 'next/cache'

export async function savePost() {
  // ...写入数据库...
  revalidatePath('/blog')      // 按路径：作废 /blog 整条路由
  revalidateTag('posts')       // 按标签：作废所有打了 posts 标签的数据
}
    revalidatePath / revalidateTag 放哪里、效果有何不同
    调用位置Data Cache客户端 Router Cache
    Server Action（用户提交表单后）作废对应条目立即失效当前路由段，界面即时更新
    Route Handler（接收第三方 Webhook）作废对应条目不立即失效，等整页刷新或自动过期

    动态 API 也能「废掉」静态缓存

    另一种常见情况：路由里一旦用了 cookies()、headers()、searchParams、connection()、draftMode() 或 fetch(..., { cache: 'no-store' })，整条路由就转为动态渲染——这意味着它不再进完整路由缓存。这不是报错，而是 Next.js 的自动降级：含有请求期信息的路由天然无法静态化。

    对照示例：让一个页面「完全静态」还是「完全动态」

    app/about/page.tsx —— 完全静态
    export const dynamic = 'force-static'

export default async function AboutPage() {
  // 没有 cookies/headers/searchParams
  // fetch 显式缓存，整页构建时生成一次，之后走完整路由缓存
  const res = await fetch('https://api.example.com/about', {
    cache: 'force-cache',
  })
  const data = await res.json()
  return <main>{data.content}</main>
}
    app/dashboard/page.tsx —— 完全动态
    export const dynamic = 'force-dynamic'
// 等价于：段内所有 fetch 默认 no-store + revalidate 0

export default async function DashboardPage() {
  // 每次请求都实时渲染：看登录态、看最新数据
  const res = await fetch('https://api.example.com/me/dashboard')
  const data = await res.json()
  return <main>{data.widgets}</main>
}
    完全静态 vs 完全动态对照
    维度完全静态完全动态
    渲染时机构建时 / 后台 ISR每次请求实时渲染
    完整路由缓存命中不命中
    数据新鲜度有重新验证延迟永远最新
    服务端成本极低每请求一次渲染
    适用官网、博客、营销页后台、个性化、实时数据

    调试：观察缓存到底有没有命中

    手段一：next build 输出符号

    跑一次生产构建，终端会列出每条路由的渲染类型，这是判断「完整路由缓存」最直接的方式：

    $ next build 输出示意
    Route (app)
  ┌ ○ /about                静态渲染（进完整路由缓存）
  ├ ● /blog/[slug]          SSG + ISR
  ├ ƒ /dashboard            动态渲染（每请求实时渲染，不进完整路由缓存）
  └ ○ /                     静态渲染
    • ○ (Static)：静态预渲染。
    • ● (SSG)：由 generateStaticParams 生成的静态页。
    • ƒ (Dynamic)：动态渲染，按请求执行。

    手段二：响应头 x-nextjs-cache

    用 curl -I 观察数据缓存状态（部署在 Vercel 等支持的平台上）：

    终端
    $ curl -I https://yourapp.com/api/posts

x-nextjs-cache: HIT     # 命中数据缓存
# 或 MISS                # 未命中，刚回源
# 或 STALE               # 数据已过期，正在后台重新验证

    手段三：Vercel 面板

    部署到 Vercel 后，在项目 Observability / 函数日志里可以看到每个请求的缓存命中情况、渲染耗时与数据请求耗时，是生产环境排查「为什么这个请求变慢了」的第一现场。

    常见坑：dev 模式观察不到真实缓存行为›

    next dev 下页面总是按需渲染、缓存被弱化（为了热更新即时反馈）。想验证本节讲的任何缓存/失效行为，都请 next build && next start 后再用 curl 观察，否则结论会和线上不符。

    最佳实践：四层缓存的取舍建议›
    1. 默认让 Next.js 静态化能静态的路由，只在确实需要请求期数据的路由上切动态。
    2. 数据层用「revalidate + tags」组合：时间兜底保鲜，标签负责事件驱动精准失效。
    3. 写操作后统一在 Server Action 里 revalidatePath/revalidateTag，不要靠用户手动刷新。
    4. 排查问题顺序：先看 next build 符号判断路由静态/动态 → 再看响应头判断数据缓存命中 → 最后看客户端是否卡在 Router Cache。
    5. Next.js 16 起官方在推动 Cache Components（use cache 指令模型），属于实验性新模型；本教程以 15 稳定行为为准，新模型可作为拓展了解。
