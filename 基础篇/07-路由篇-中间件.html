路由篇 | 中间件

在请求抵达路由之前跑一段代码：用中间件做鉴权重定向、路径改写、读写请求/响应头与 Cookie，以及它和服务端守卫的取舍。

篇章：基础篇主题：路由 · Middleware篇幅：约 12 分钟

本节目录

    概念与背景

    Next.js 中间件（Middleware）允许你在请求完成之前运行一段服务端代码，然后根据入站请求改写（rewrite）、重定向（redirect）、修改请求或响应头，甚至直接返回响应。它处在请求链路最靠前的位置：在路由（页面 page.tsx 或路由处理程序 route.ts）被处理之前执行。

    典型用途包括：登录态校验与未登录重定向、基于 Cookie/请求头的国际化（i18n）路由、A/B 测试分流、把旧 URL 重写到新页面、按地区返回不同内容、添加安全响应头（如内容安全策略）等。

    一个关键点：中间件默认运行在边缘运行时（Edge Runtime），而不是 Node.js 服务端运行时。这意味着它执行快、可以被部署到离用户最近的边缘节点，但同时也有 Node 专有 API（如访问本地文件系统、长连接）不可用的限制——这部分在第 27 节「Edge Runtime」会展开。

    浏览器请求
    →
    中间件执行
    (Edge Runtime)
    →
    路由段处理
    page.tsx / route.ts
    →
    返回响应

    文件约定与基本结构

    中间件通过文件约定启用：在项目根目录（或 src/ 同级）创建 middleware.ts（或 .js），默认导出一个名为 middleware 的函数即可，无需在任何地方注册。

    middleware.ts（项目根或 src/ 下）
    import { NextResponse } from "next/server"
import type { NextRequest } from "next/server"

// 每个命中 matcher 的请求都会先进入这个函数
export function middleware(request: NextRequest) {
  // request 是增强版的请求对象，可以读路径、Cookie、请求头
  if (request.nextUrl.pathname === "/about") {
    // 返回一个响应：重定向 / 改写 / 直接响应
    return NextResponse.redirect(new URL("/home", request.url))
  }
  // 不放行任何响应时，等价于 NextResponse.next()，请求继续往后走
  return NextResponse.next()
}

// 可选：配置哪些路径跑中间件（见下一节）
export const config = {
  matcher: ["/about/:path*"],
}

    matcher：控制中间件在哪些路径上运行

    如果你不显式配置 matcher，中间件会对每一个请求都执行一遍——这往往不是你想要的。matcher 用来精确过滤目标路径：支持单个字符串、路径数组、路径分段（:path*）以及负向排除。

    middleware.ts — matcher 配置示例
    export const config = {
  matcher: [
    // 匹配单个路径
    "/about",
    // 匹配路径及其所有子路径
    "/dashboard/:path*",
    // 排除静态资源与内部文件的常见写法（负向先行断言）
    "/((?!api|_next/static|_next/image|favicon.ico).*)",
  ],
}

    matcher 内部基于路径前缀匹配，也支持正则式的路径段语法。想避免中间件被静态资源（图片、_next/static 下的打包产物）频繁触发，是实际项目里最常见的一条配置。

    常见坑：matcher 与手动判断要二选一›

    不要既写宽泛的 matcher 又在函数里用 request.nextUrl.pathname.startsWith(...) 反复过滤。官方推荐用 matcher 把「命中范围」声明清楚，函数体只负责业务逻辑；两层过滤容易让后续维护者误判哪些路径真的会进中间件。

    NextRequest 与 NextResponse

    中间件的入参 NextRequest 是对原生请求的扩展：在标准 Request 之上加了 nextUrl（解析好的路径、查询参数、locale）以及便捷的 cookies、geo、ip 等字段。返回值用 NextResponse 构造。

    rewrite() 与 redirect() 的区别

    rewrite（改写）vs redirect（重定向）
    方法行为浏览器地址栏
    NextResponse.rewrite(url)服务端内部把请求转发到另一个路径，用户感知不到保持原 URL 不变
    NextResponse.redirect(url)返回 3xx 响应，浏览器发起一次新请求地址栏变为新 URL
    middleware.ts — rewrite 示例（对用户透明）
    import { NextResponse } from "next/server"
import type { NextRequest } from "next/server"

export function middleware(request: NextRequest) {
  const url = request.nextUrl
  // 访问 /home 时，地址栏仍是 /home，实际渲染 /dashboard
  if (url.pathname === "/home") {
    return NextResponse.rewrite(new URL("/dashboard", request.url))
  }
}

    读写请求头 / 响应头 / Cookie

    中间件是唯一能在「路由处理之前」统一加工请求与响应的地方：可以读传入的请求头/Cookie，也可以往回写响应头、种 Cookie。改请求头用 NextResponse.next({ request: { headers } })，写响应直接在返回的 response 上操作。

    middleware.ts — 读写 Cookie 与请求头
    import { NextResponse } from "next/server"
import type { NextRequest } from "next/server"

export function middleware(request: NextRequest) {
  // 1) 读 Cookie
  const token = request.cookies.get("session")?.value

  // 2) 基于 Cookie 决定：放行时向下游路由注入一个请求头
  const requestHeaders = new Headers(request.headers)
  requestHeaders.set("x-user-token", token ?? "")

  // 3) 构造响应并往回写响应头 / 种 Cookie
  const response = NextResponse.next({
    request: { headers: requestHeaders },
  })
  response.headers.set("x-middleware-cache", "hit")
  if (!token) {
    response.cookies.set("anon-id", crypto.randomUUID(), {
      httpOnly: true,
      sameSite: "lax",
    })
  }
  return response
}

    完整示例：未登录访问受保护路由时重定向到登录页

    这是最常见的真实场景：把 /dashboard/* 划为受保护区域，没有会话 Cookie 就跳登录页，并把当前路径作为回跳地址带过去。

    middleware.ts — 鉴权重定向
    import { NextResponse } from "next/server"
import type { NextRequest } from "next/server"

const PUBLIC_ROUTES = ["/login", "/signup"]

export function middleware(request: NextRequest) {
  const { pathname, search } = request.nextUrl

  // 1) 是否命中受保护区域
  const isProtected = pathname.startsWith("/dashboard")
  const isPublic = PUBLIC_ROUTES.some((p) => pathname.startsWith(p))

  const session = request.cookies.get("session")?.value

  // 2) 未登录访问受保护页 → 跳登录，并记录原路径
  if (isProtected && !session) {
    const loginUrl = new URL("/login", request.url)
    loginUrl.searchParams.set("from", pathname + search)
    return NextResponse.redirect(loginUrl)
  }

  // 3) 已登录还访问登录页 → 直接进后台
  if (isPublic && session) {
    return NextResponse.redirect(new URL("/dashboard", request.url))
  }

  return NextResponse.next()
}

export const config = {
  // 只拦截 dashboard 与登录相关路径，避免每个静态资源都跑中间件
  matcher: ["/dashboard/:path*", "/login", "/signup"],
}

    登录页拿到 from 参数后，登录成功就 router.push(from) 回原页面，形成完整闭环。

    中间件 vs 服务端守卫：该把权限校验放哪？

    App Router 的页面/布局本身就是服务端组件，天然能读 Cookie、做鉴权。那为什么还需要中间件？两者解决的是「拦截时机与粒度」的不同问题：

    中间件与服务端守卫（layout/page 内校验）取舍
    维度中间件 Middleware服务端组件内守卫（layout/page）
    执行时机路由处理之前，最早渲染该路由段时
    运行时Edge Runtime，无 Node 生态Node.js Runtime（或 Edge）
    擅长路由级门禁：整组路径统一鉴权、改写、重定向、加头页面内细粒度授权：按数据/角色决定渲染内容
    不擅长重业务校验、复杂数据库查询、Node 依赖想在渲染前就拦截整组路径、做路径改写/分流
    经验法则：路由级、跨多页、只看 Cookie/请求头就能下判断的门禁放中间件；需要查数据库、按具体业务对象授权的，放在对应 layout.tsx 或 page.tsx 里（通常配合服务端校验后 redirect()）。
    最佳实践›
    • matcher 显式排除 _next/static、_next/image、静态资源，减少无谓执行。
    • 中间件保持「轻」：只做路由决策（重定向/改写/加头），把重业务逻辑下沉到路由处理或服务端组件。
    • 鉴权 Cookie 一律 httpOnly，中间件读它而不是让前端读——避免 XSS 偷会话。
    • 需要在中间件和页面间传递轻量判断结果时，用自定义请求头（如 x-user-id），页面里用 headers() 读取。
    提示：NextResponse.next() 可以省略›

    中间件函数如果没有返回任何 NextResponse，效果等同于调用 NextResponse.next() 放行。只有当你要改写下游拿到的请求头/Cookie 时，才需要显式 return NextResponse.next({ request: { headers } })。
