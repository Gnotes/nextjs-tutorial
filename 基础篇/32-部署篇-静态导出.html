部署篇 | 静态导出

通过 output: 'export' 把 Next.js 构建成纯静态 HTML/CSS/JS 产物（out/ 目录），从而部署到任意静态托管：GitHub Pages、对象存储、Nginx。本节讲清配置方式、产物结构、完整的支持/不支持能力清单，以及与历史命令 next export 的区别。

篇章：部署篇主题：静态导出对应小册：第 32 节

本节目录

    概念与背景

    静态导出（Static Exports）让 Next.js 既能以静态站点或单页应用（Single Page Application，SPA）起步，将来再按需升级到需要服务器的功能。运行 next build 时，Next 会为每个路由生成一个独立的 HTML 文件。相比把整个应用打包成一个空壳，这种「按路由切分」的做法能让浏览器少下载无关 JavaScript，包体积更小、首屏更快。

    核心收益是：构建产物全是静态资源，因此可以部署到任何能托管 HTML/CSS/JS 的地方，完全不需要 Node.js 服务器运行时——成本最低、抗流量能力最强。代价是：所有需要在请求时动态计算的能力都不能用（下文清单）。

    next build 构建时
    预渲染各路由
    →
    生成 out/
    HTML/CSS/JS
    →
    上传到静态托管
    (GitHub Pages/S3/Nginx)
    →
    请求直接命中文件
    无需服务器

    开启配置与产物结构

    在 next.config.js 里把 output 设为 'export'：

    next.config.js
    /**
 * @type {import('next').NextConfig}
 */
const nextConfig = {
  output: 'export',
  // 可选：把 /me 生成为 /me/index.html（而非 /me.html）
  // trailingSlash: true,
  // 可选：改输出目录名 out → dist
  // distDir: 'dist',
}

module.exports = nextConfig

    构建后 Next 会在项目根生成 out/ 目录。假设有路由 / 与 /blog/[id]（且通过 generateStaticParams 声明了 post-1、post-2），产物形如：

    out/ 产物目录
    out/
├── index.html          # 对应路由 /
├── 404.html
└── blog/
    ├── post-1.html     # 对应 /blog/post-1
    └── post-2.html

    注意 out/ 是导出目录，不是构建缓存目录；真正的构建中间产物在 .next/，静态导出时把可部署的最终资源汇总到了 out/。

    支持的能力

    • React Server Components (RSC)：构建时会在服务端执行一次，渲染成静态 HTML，客户端导航时再用静态 payload 过渡，无需改动代码。
    • 客户端组件数据请求：可以在客户端组件里用 SWR（Stale-While-Revalidate）等库做浏览器端取数，路由切换退化成传统 SPA 行为。
    • 路由处理程序（Route Handlers）：只有 GET 方法会被支持，构建时渲染成静态响应文件（如 app/data.json/route.ts → out/data.json）。凡是要读取请求动态值的路由处理程序都不行。
    • 图片优化：默认 loader 不支持，需在 next.config.js 配置自定义 loader（如接 Cloudinary 这类图片服务）。
    • 浏览器 API：window、localStorage 等只在客户端可用，需放在 useEffect 里安全访问。
    next.config.js（图片自定义 loader）
    const nextConfig = {
  output: 'export',
  images: {
    loader: 'custom',
    loaderFile: './my-loader.ts',
  },
}
module.exports = nextConfig

    不支持的能力（限制清单）

    凡是需要 Node.js 服务器、或无法在构建期算出来的动态逻辑，静态导出都不支持：

    output: 'export' 下不支持 / 受限的能力
    能力原因 / 说明
    动态路由 dynamicParams: true无法在构建期枚举出全部动态路径。
    未提供 generateStaticParams 的动态路由构建时不知道要生成哪些页面。
    依赖请求的 Route Handlers只有 GET 静态响应可用，读不到请求体/查询动态值。
    Cookies（cookie 读取）请求期才能知道的信息，构建期不存在。
    Rewrites / Redirects / Headers这些是服务端运行期行为，没有服务器就无从执行。
    Middleware（中间件）中间件运行在服务端，静态导出无运行时。
    增量静态再生成（ISR）ISR 需要在运行期后台重新生成页面，纯静态做不到。
    默认 loader 的图片优化优化需要服务端实时处理图片，需换自定义 loader。
    Draft Mode（草稿模式）依赖旁路 cookie + 动态渲染。
    Server Actions（服务端动作）需要服务端接收并执行动作。
    Intercepting Routes（拦截路由）运行期路由拦截能力。
    常见坑：用了不支持的能力会直接报错›

    在 next dev 里使用上述任何不支持能力，Next 会直接报错——其效果等价于在根 layout 设置了 export const dynamic = 'error'。这是好事：它在开发阶段就阻止你写出「能开发、不能导出」的页面。

    与 Pages Router 的 next export 历史区别

    在 Pages Router 时代，静态导出是一条独立命令：先 next build 再跑 next export（或 package.json 里 "export": "next build && next export"）。这套机制已经演进：

    next export（旧） vs output: 'export'（新）
    维度next export（Pages Router，旧）output: 'export'（App Router，新）
    触发方式独立 CLI 命令 next exportnext.config 里配置后随 next build 自动产出
    状态v13.3 废弃，v14 彻底移除现行推荐方式
    能力仅 SSG 页面导出支持 RSC、Route Handlers 静态响应等增强

    结论：现在统一用 output: 'export'，不要再使用 next export 命令。

    部署到静态托管

    out/ 目录可以直接上传到任意静态托管服务。以 Nginx 为例，需要把请求重写到对应 .html 文件：

    nginx.conf
    server {
  listen 80;
  server_name acme.com;
  root /var/www/out;

  location / {
    # 依次尝试 $uri、$uri.html、$uri/，都不中则 404
    try_files $uri $uri.html $uri/ =404;
  }

  # trailingSlash: false 时需要这条重写；true 时可省略
  location /blog/ {
    rewrite ^/blog/(.*)$ /blog/$1.html break;
  }

  error_page 404 /404.html;
  location = /404.html { internal; }
}

    其他常见托管方式：GitHub Pages 直接把 out/ 作为发布目录推上去；对象存储（如 S3、OSS）把 out/ 整个桶开启静态网站托管即可。这些平台都无需运行 Node。

    最佳实践›
    1. 开了 output: 'export' 后，动态路由必须配 generateStaticParams，必要时加 export const dynamicParams = false 让未知路径直接 404。
    2. 选静态托管前先对照上面的不支持清单自查——一旦项目需要登录态、Server Actions、草稿预览，就不该走纯静态导出。
    3. 需要服务端能力时，可以渐进迁移：先静态上线官网/文档，把需要服务的部分拆到独立服务，而不是一开始就上重型服务器。
