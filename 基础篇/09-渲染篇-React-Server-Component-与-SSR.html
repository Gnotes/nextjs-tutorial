渲染篇 | React Server Component 与 SSR

RSC 不是又一种渲染时机，而是一套全新的组件与数据协议：服务端组件在服务端执行、不打进客户端 JS。本节讲清它和 SSR 的本质区别。

篇章：基础篇主题：渲染 · RSC篇幅：约 14 分钟

本节目录

    从第 08 节说起：先纠正一个常见误解

    第 08 节我们按「HTML 在哪里、什么时候生成」把渲染方式分成了客户端渲染（Client-Side Rendering，CSR）、服务端渲染（Server-Side Rendering，SSR）、静态站点生成（Static Site Generation，SSG）和增量静态再生成（Incremental Static Regeneration，ISR）。这四个回答的是渲染时机与位置的问题。

    而 React Server Components (RSC，React 服务端组件)不是在这条轴上新加的第五种渲染方式——它是另一层东西：一套全新的组件模型与数据传输协议。混淆这两件事，是理解 RSC 时最容易踩的坑。本节的目标就是把这两层彻底分开。

    RSC 是什么：一场组件模型革命

    在 RSC 出现之前，React 组件只有一种形态：它既会在服务端被渲染（SSR/SSG），也会被打包进浏览器下载、在客户端水合后继续运行。也就是说，同一份组件代码，既在服务端跑、也在客户端跑。

    RSC 把组件分成了两类：

    • 服务端组件（Server Component）：只在服务端执行，永远不会被打包进客户端 JavaScript。它们执行完之后，渲染结果会被序列化成一份「指令流」发给浏览器。
    • 客户端组件（Client Component）：文件顶部加 "use client" 指令，才会被打进客户端 bundle，参与水合和交互（第 11 节展开）。

    App Router 的默认假设就是：不加任何指令的组件就是服务端组件。这和 Pages Router 里「所有组件默认都是客户端组件」正好相反，是心智模型上最大的一次翻转。

    为什么需要 RSC：它到底解决了什么

    • 减少客户端 JS：大量与交互无关的组件（布局、展示、数据列表）根本不用发到浏览器，首屏加载的脚本体积显著下降。
    • 组件可以直接读数据库：因为服务端组件跑在服务端，它内部可以直接查询数据库、访问文件系统、调用服务端专用 SDK，而不必为每个数据源都额外暴露一个网络接口。
    • 数据获取与渲染合并：以前「先请求接口、再渲染组件」的两段式流程，变成组件内部直接取数，减少了来回网络往返（Waterfall）。
    • 天然安全：服务端组件里的密钥、数据库连接、权限判断永远不会泄漏到客户端 bundle。

    RSC Payload：浏览器到底收到了什么

    这是理解 RSC 的关键机制。服务端执行完一整棵组件树后，不会只吐一段 HTML，而是生成一份特殊的序列化数据，官方称为 RSC Payload，其底层使用 React 的 Flight 协议（一种流式序列化格式）。这份 payload 混合了两类东西：

    • 已经渲染好的 HTML 片段（服务端组件的输出）；
    • 对客户端组件的「引用」——只告诉客户端「这里有一个客户端组件， props 是这些序列化后的值，组件代码在哪」，客户端据此再水合。
    请求页面
    →
    服务端执行组件树
    服务端组件直接读库
    →
    生成 RSC Payload
    (Flight 序列化流)
    →
    浏览器拼接
    HTML + 组件引用
    →
    水合客户端组件
    变为可交互

    换句话说：服务端组件本身不水合——它们的输出就是静态的 HTML 树，浏览器拿到后直接插进页面；只有被标记为客户端组件的那一小部分，才需要下载 JS 并水合。这也是 RSC 能大幅减少交互就绪时间的根本原因。

    RSC 与 SSR 的本质区别

    很多人把 RSC 和 SSR 混为一谈，是因为「服务端组件最终也是在服务端渲染成 HTML」。但两者回答的问题不在一个层面：

    RSC（组件/数据协议） vs SSR（渲染时机）
    维度RSC（React Server Components）SSR（Server-Side Rendering）
    它是什么组件模型 + 数据序列化协议（Flight）一种渲染策略：HTML 在请求时于服务端生成
    解决的问题组件该不该发到客户端、数据怎么跨服务端/客户端传输首屏内容与 SEO，让浏览器拿到有内容的 HTML
    组件是否打进客户端 JS服务端组件不进客户端 bundleSSR 渲染过的组件仍然要全部水合、全部下载 JS
    数据获取组件内直接读数据库/服务端资源通常先取数再渲染，数据与组件分离
    二者关系在 App Router 里，RSC 是默认组件模型；它既可以配合静态生成，也可以配合流式 SSR 输出 HTML——两者是「正交」关系，不是二选一
    一句话记忆：SSR 回答「HTML 什么时候、在哪里生成」，RSC 回答「哪些组件属于服务端、它们的结果用什么协议传过去」。App Router = RSC 组件模型 + 默认偏向静态/流式的渲染策略。

    示例：服务端组件直接读数据库

    下面这个页面是一个默认服务端组件（没有 "use client"），它直接在函数体里查询数据库，再把数据交给纯展示子组件。整个过程没有任何接口请求、没有任何客户端 JS。

    app/blog/page.tsx（服务端组件，直接读库）
    // 默认就是服务端组件：本文件不会被打进客户端 bundle
// 这里可以安全地 import 服务端专用库（数据库 SDK、密钥等）
import { db } from "@/lib/db"

type Post = { id: string; title: string; createdAt: string }

export default async function BlogPage() {
  // 服务端组件可以是 async 的：直接在服务端读数据库
  const posts: Post[] = await db.post.findMany({
    orderBy: { createdAt: "desc" },
    take: 20,
  })

  return (
    <main>
      <h1>最新文章</h1>
      <ul>
        {posts.map((post) => (
          <li key={post.id}>
            <a href={`/blog/${post.id}`}>{post.title}</a>
          </li>
        ))}
      </ul>
    </main>
  )
}

    注意三点：① 组件是 async 函数，可以直接 await；② 里面 import 的数据库 SDK 永远不会发到浏览器；③ 这个组件树产出的是 RSC Payload 的一部分，而不是一段必须整体水合的 CSR 代码。

    常见坑：async 服务端组件里别写交互›

    服务端组件不能用 useState、useEffect、事件监听、浏览器 API（window、localStorage）。一旦需要交互，就把那一小块 UI 抽成一个加了 "use client" 的客户端组件，再由服务端组件引用它——这正是第 11 节要讲的组合模式。

    提示：RSC Payload 在 dev 里可以直接观察›

    用 curl 请求一个 App Router 页面时，响应体里能看到 Flight 格式的数据（以 self.__next_f.push(...) 开头的分片），那就是 RSC Payload。它和「浏览器最终看到的 HTML」不是一回事——这正是 RSC 区别于传统 SSR 的直观证据。

    最佳实践：默认服务端组件，按需下沉到客户端›
    • 新写组件先不加 "use client"，默认让它当服务端组件；只有用到 hooks / 事件 / 浏览器 API 时才标记为客户端组件。
    • 把「能在服务端做的事」（取数、过滤、权限判断、格式化）尽量留在服务端组件里，减少暴露给客户端的逻辑与密钥。
    • 数据获取优先放在离渲染它的组件最近的服务端组件里，配合 Suspense 做流式分段（第 10 节）。
