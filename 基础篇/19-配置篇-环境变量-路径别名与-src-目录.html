配置篇 | 环境变量、路径别名与 src 目录

本节讲三件日常开发高频用到的工程配置：环境变量（.env 系列）的加载顺序与 NEXT_PUBLIC_ 前缀的安全边界、TypeScript 路径别名 @/* 的配置、以及把 app 目录放进 src/ 下的约定。

本节目录

    环境变量：.env 系列文件

    Next.js 内置了对 .env 文件的支持，你不需要安装任何额外的库。约定的文件名有四种，按环境自动加载：

    • .env：所有环境都加载，可提交到仓库（一般放非敏感默认值）。
    • .env.local：所有环境都加载，但会被 git 忽略，通常放本地覆盖值与密钥。
    • .env.development：仅在 next dev（开发）时加载。
    • .env.production：仅在 next build / 生产启动时加载。

    加载是"找到即停"的，优先级从高到低：

    1. process.env（系统已设置的变量，最高优先级）
    ↓
    2. .env.$(NODE_ENV).local（如 .env.development.local）
    ↓
    3. .env.local（NODE_ENV=test 时跳过）
    ↓
    4. .env.$(NODE_ENV)（如 .env.production）
    ↓
    5. .env（最低优先级）
    .env.local
    # 服务端变量（不会暴露给浏览器）
DB_URL="postgresql://user:pass@localhost:5432/mydb"
API_SECRET="sk-xxxxxxxxxxxx"

# 客户端变量（加 NEXT_PUBLIC_ 前缀，会内联进浏览器 JS）
NEXT_PUBLIC_API_BASE="https://api.example.com"
NEXT_PUBLIC_APP_NAME="我的 Next 应用"

    在代码中读取

    服务端代码（服务端组件、路由处理程序、Server Actions）直接读 process.env.XXX：

    app/page.tsx（服务端组件）
    // 这个组件默认在服务端运行，可以直接读服务端变量
export default async function Page() {
  // 服务端变量：安全，不会出现在浏览器
  const dbUrl = process.env.DB_URL;
  // 客户端变量：加了 NEXT_PUBLIC_，两边都能读
  const apiBase = process.env.NEXT_PUBLIC_API_BASE;

  return (
    <main>
      <p>API 地址：{apiBase}</p>
      <!-- 注意：dbUrl 不要渲染到页面上，否则会被用户看到 -->
    </main>
  );
}

    NEXT_PUBLIC_ 前缀：安全边界

    这是最容易踩坑的一条规则：默认情况下，环境变量只在 Node.js 服务端可用，浏览器里拿不到。想让浏览器端代码（客户端组件、事件回调）也能访问，必须给变量名加 NEXT_PUBLIC_ 前缀。

    原理是：构建（next build）时，Next.js 会把所有 NEXT_PUBLIC_* 的值文本内联（Inline）进 JavaScript 产物。这意味着：

    • 客户端组件里写 process.env.NEXT_PUBLIC_API_BASE，构建后会被替换成字面量字符串。
    • 因此 NEXT_PUBLIC_ 变量的值会进入最终 JS Bundle，任何人都能在浏览器源码里看到——它不是保密通道。
    • 密钥、数据库连接串、Token 等敏感值绝不能加这个前缀。
    常见坑①：改了 .env 但没重启开发服务器›

    环境变量在服务启动时一次性加载，修改 .env* 文件后必须重启 next dev 才生效。NEXT_PUBLIC_ 变量还与构建产物绑定，next build 后想换公网地址也要重新构建，不能靠改运行时环境变量。

    常见坑②：在客户端组件里读未加前缀的变量›

    在 "use client" 组件里读 process.env.DB_URL 会得到 undefined。因为服务端变量不会被内联进浏览器 JS。如果逻辑里同时用到两种变量，让服务端组件先读取、再通过 props 传给客户端组件。

    提示：运行时环境变量与构建时内联的区别›

    服务端变量（如 DB_URL）在每次服务启动时从运行时环境读取，部署平台（Vercel / Docker）可在不重新构建的情况下更换。而 NEXT_PUBLIC_* 是构建时内联的，更新它们必须重新 next build。需要运行时动态公网值时，用路由处理程序（Route Handler）在服务端读取再返回给前端。

    路径别名 @/*：告别 ../../

    项目层级深了之后，import Button from "../../../components/Button" 这种相对路径既难写又易错。Next.js 在 TypeScript 项目中默认通过 tsconfig.json 的 paths 字段支持 @/* 别名，Webpack 与 Turbopack 都会自动识别，无需额外配置。

    tsconfig.json
    {
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["./*"]
    }
  }
}

    配置之后，任意深度的文件都可以用绝对别名导入：

    app/dashboard/settings/page.tsx
    // 之前：import Header from "../../components/Header";
// 现在：从项目根开始，永远不需要数 ../
import Header from "@/components/Header";
import { formatDate } from "@/lib/utils";

    用 JavaScript 项目（无 tsconfig）时，可新建 jsconfig.json 写同样的 compilerOptions.paths，编辑器（VS Code）与 Next.js 都会识别。

    src 目录：把 app 放进源码根

    默认项目结构是 app/、public/ 直接位于项目根。如果你习惯把所有源码收进 src/ 目录，Next.js 支持把 app/ 移到 src/app/——框架会自动识别，不需要任何配置。

    项目结构对比
    # 默认结构
my-app/
├── app/
│   ├── layout.tsx
│   └── page.tsx
├── public/
└── package.json

# 使用 src 目录后的结构（Next.js 自动识别）
my-app/
├── src/
│   ├── app/
│   │   ├── layout.tsx
│   │   └── page.tsx
│   └── components/
├── public/
└── package.json
    注意：app 与 src/app 只能二选一›

    如果项目根同时存在 app/ 和 src/app/，Next.js 会优先使用项目根的 app/ 并发出警告。迁移时把整个 app/ 目录一次性移动到 src/app/，别留空壳。public/、next.config.js 仍留在项目根，不放进 src/。

    完整示例串起来

    把三件事合在一个典型项目里：

    .env.local + tsconfig.json + 读取代码
    # .env.local
SERVICE_API="https://internal.service/api"   # 服务端
NEXT_PUBLIC_SITE_TITLE="我的博客"              # 客户端

// tsconfig.json 关键片段
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": { "@/*": ["./src/*"] }
  }
}

// src/app/page.tsx（注意 app 在 src 下）
import Header from "@/components/Header";

export default function Page() {
  return <Header title={process.env.NEXT_PUBLIC_SITE_TITLE} />;
}
    最佳实践：环境变量管理约定›
    1. .env 提交到仓库，放非敏感默认值；.env.local 放密钥并加入 .gitignore（create-next-app 默认已忽略）。
    2. 所有要给浏览器用的变量统一加 NEXT_PUBLIC_，并在文档里列出清单；服务端变量一律不加前缀。
    3. 提交一份 .env.example 列出项目需要的所有变量名（不含真实值），方便新成员与部署平台配置。
    4. 统一使用 @/* 别名导入组件与工具函数，禁止深层相对路径。
